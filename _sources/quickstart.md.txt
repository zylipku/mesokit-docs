# Quickstart

Install `mesokit`, generate a dataset, train a model, and extract an
interpretability artifact — end to end. Every command runs from a
**project directory**: the folder where `mesokit` keeps the datasets it
generates (`data/`), the checkpoints, the figures and its `.mesokit/`
registries. Any directory works; nothing has to be written by hand there.

(installation)=

## Installation

There are two ways to install, for two kinds of use.

**Use the toolkit as a package.** Built-in simulators, the three model
families, training and interpretation are all reachable from the `mesokit`
command; the shipped recipes travel with the package, and the grid of a
model is read from the dataset, so no configuration file needs writing:

```bash
pip install mesokit           # from PyPI (release pending; from a clone: pip install .)
mkdir my-project && cd my-project
mesokit data avail
mesokit agent init            # optional: set up Claude Code / Codex for this project
```

A pip install lacks only two solver back-ends that are conda-forge
packages rather than PyPI ones: Dedalus, behind `allen_cahn_1d`,
`allen_cahn_2d` and `kdv_1d`, and LAMMPS, behind
`peridynamics_fracture_2d`. Those four simulators stay listed and, when
run, stop with a message naming the package to add; everything else,
training and interpretation on any dataset included, works as is. To have
them too, install mesokit into an environment that also holds the two
packages. With conda:

```bash
conda create -n mesokit -c conda-forge python=3.12 dedalus lammps
conda activate mesokit
pip install mesokit
```

Or as a [pixi](https://pixi.sh) project, which resolves conda-forge and
PyPI together:

```bash
pixi init my-project && cd my-project
pixi add python=3.12 dedalus lammps     # from conda-forge
pixi add --pypi mesokit                 # from PyPI
```

**GPU and torch.** mesokit depends on `torch>=2.9,<2.11`. Up to 2.10 the
default torch wheel on PyPI is a CUDA 12.8 build, which runs on any CUDA
12.x or 13.x driver, so a plain install works on a GPU machine with no
PyTorch index to choose (from 2.11 the default wheel needs a CUDA 13
driver, which is why the bound is there). A machine without a GPU can skip
the CUDA libraries, about 3 GB, by installing CPU torch first:

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu      # then: pip install mesokit
pixi add --pypi --index https://download.pytorch.org/whl/cpu torch      # pixi: then pixi add --pypi mesokit
```

Until the PyPI release, install from a clone instead of `pip install
mesokit` (`pip install /path/to/mesokit`), or point the pixi project at
it: `mesokit = { path = "/path/to/mesokit" }` under `[pypi-dependencies]`
in its `pixi.toml`, then `pixi install`.

**Extend the toolkit.** Your own simulators, models, trainers or
artifacts are Python. Work from a checkout, whose [pixi](https://pixi.sh)
environment provides an editable install, and put your code in its
`plugins/` folder — gitignored, imported by every `mesokit` command, so a
model registered there is used by name like a shipped one:

```bash
git clone <this-repo> mesokit
cd mesokit
pixi install
cp ~/my_models.py plugins/          # @register("my_model_1d") inside
pixi run mesokit train --model my_model_1d --data <dataset>
```

Prefix commands with `pixi run` (or open a pixi shell by running `pixi
shell`) if `mesokit` is not on your `PATH`. The *Custom* pages of this
guide assume this layout; a `plugins/` folder in any project directory
works the same way.

Both need a linux-64 platform with a CUDA-capable GPU (CUDA 12.6 or newer).
This page shows the happy path; every option, output file, error message
and more examples are in the [Command-Line Reference](cli.md).

## Two Ways to Follow This Guide

Every step below is a command or a short script you can run yourself. If
you use a coding agent (Claude Code, Codex CLI), each step is also a
*skill* the agent can carry out for you — converting your data, choosing
and training a model, extending mesokit with your own equation or model.
See [Agent Skills](skills.md) for what they do and how to install them
(in your own project, `mesokit agent init` sets the agent up in one step);
the commands the agent runs are the ones documented here.

## Data Loading

To see the catalog of pre-defined simulator recipes:

```sh
mesokit data avail   # alias: mesokit data available
```

To see which datasets are actually registered on this machine — grouped
by dynamics, with `custom:` at the bottom for entries whose `dyn` isn't a
registered simulator — and the cache path for each:

```sh
mesokit data list
```

### Generating From a Predefined Recipe

Pre-defined datasets are generated on demand. The resulting file is
auto-registered so the next `mesokit data list` shows it as cached and
downstream commands can refer to it by name. With no `--name`, the dataset
is registered as `<dyn>_v0`; repeated runs (e.g. with different parameters)
get `_v1`, `_v2`, …. With no `--output`, the file is written to
`data/<dyn>/<name>.h5`:

```sh
mesokit data generate --dyn allen_cahn_1d                                          # data/allen_cahn_1d/allen_cahn_1d_v0.h5
mesokit data generate --dyn allen_cahn_1d                                          # data/allen_cahn_1d/allen_cahn_1d_v1.h5 # repeated run -> v1
mesokit data generate --dyn allen_cahn_1d --name my_run                            # custom name -> data/allen_cahn_1d/my_run.h5
mesokit data generate --dyn allen_cahn_1d --output data/scratch.h5 --no-registry   # explicit path, skip registration
```

`--name` and `--no-registry` are mutually exclusive.

Each dynamics has its own config folder under `configs/data/<dyn>/`, with a
`default.yaml` used when `--config` is not passed. To run a variant config,
drop a sibling YAML next to `default.yaml` and select it by stem (no extension):

```sh
mesokit data generate --dyn allen_cahn_1d --config fdr    # reads configs/data/allen_cahn_1d/fdr.yaml
```

Pass `--verbose` to surface the underlying solver's per-step logs (default
is a single concise progress line on stderr).

### Registering a Custom Dataset

For data produced outside `mesokit` (a separate solver, MD trajectories,
a finite-difference export), write an HDF5 file that follows the cache
contract and register it under a name:

```sh
mesokit data register --name DATASET_NAME --file data/my_data.h5
```

This runs a sanity check to verify the file is in the expected format and
prints the inferred metadata (state shape, time step, …) for confirmation.
The full cache-file contract — required datasets, root attributes, and
metadata groups — is documented in [Data Processing](data_processing.md), with
end-to-end snippets in [Examples](data_processing/examples.md).

### Parsing An Arbitrary Dataset With An Agent

If your data is in a format that does not already match the cache
contract (xarray, raw numpy, torch tensors + JSON/YAML metadata, …), you
can hand the conversion off to an LLM coding agent you already have
installed. `mesokit data parse` points the agent at the cache-contract
skill shipped with the package, plus your file, and (optionally) any
extra hints; on success it validates the produced HDF5 and — when
`--name` is given — registers it the same way `mesokit data register`
would.

```sh
mesokit data parse --file path/to/raw_data.nc \
  --hint "time dim is `t`, var is `u`" \
  --agent claude \
  --name from_agent
```

Flags:

- `--agent`: which agent CLI to invoke (`claude`, `codex`). The command
  checks for it before doing anything else; if it is not installed it
  stops and points you at the official installation guide
  ([Claude Code](https://code.claude.com/docs/en/setup),
  [Codex CLI](https://developers.openai.com/codex/cli)).
- `--backend`: `foreground` (default; streams the agent's output and
  blocks) or `tmux` (detaches into a session you can attach to later).
- `--hint`: free-form prompt fragment appended to the task.
- `--output`: where to write the converted HDF5; defaults to
  `data/parsed/<input_stem>.h5`.
- `--name`: register the output under this name on success.

The same skill, plus five more for training and extending, can be used
conversationally in your agent; see [Agent Skills](skills.md).

## Training Models

Training is routed through trainer classes under `mesokit.trainers`
(the full picture, including the Python API, is in [Training](training.md)).
The CLI keeps the surface uniform: `--model` resolves the architecture,
`--trainer` optionally overrides the default trainer, and `--data` can be
either a registered dataset name or a path to an HDF5 file.

To train Spectral OnsagerNet on a registered Allen-Cahn dataset:

```sh
mesokit train \
  --model spectral_onsagernet_1d \
  --dyn allen_cahn_1d \
  --data allen_cahn_1d_v0 \
  --config default
```

`--dyn` can be omitted (it is read from the dataset), and so can the grid:
`Nx`, `Lx` and friends are filled from the dataset's metadata. The shipped
recipes under `configs/train/<dyn>/<model>/` come with the package; each
selects the model constructor, the `TrajectoryDataset` wrapper (for example
`SnapshotPairDataset`), dataloader options, and trainer hyperparameters,
and any key can be changed for one run with `--set`. Without a recipe for
a dataset / model pair, built-in defaults are used. Convenience overrides
are available for common knobs:

```sh
mesokit train --model spectral_onsagernet_1d --data allen_cahn_1d_v0 \
  --epochs 5 --batch-size 8 --device cpu --set trainer.lr=1e-4
```

The trainer writes a run directory at `checkpoints/<dyn>/<run_id>/`
containing `model.pt` (plain `state_dict`, no Lightning required to load),
`config.yaml`, and `history.json`. Unless `--no-registry` is passed, the
run is registered in `.mesokit/checkpoints.json` under `--name` or the
next `<model>_v<n>` slot.

To list registered checkpoints:

```sh
mesokit model list
```

To register an externally trained checkpoint:

```sh
mesokit model register --model MODEL_NAME --file path/to/checkpoint.pt --config path/to/config.yaml
```

This adds the model to the registry, making it available for downstream
evaluation and comparison.

## Interpretability Artifacts

Some models optionally produce an `InterpretabilityArtifact` — a
structured, self-describing object containing a human-readable view of
what the model learned (a learned free-energy landscape, a per-mode error
spectrum, …); see [Interpretability](interpretability.md) for the contract
and how to read the shipped artifact.

To see available artifacts for a registered model:

```sh
mesokit interpret list --model MODEL_NAME
```

To extract and visualize one:

```sh
mesokit interpret extract --model MODEL_NAME --artifact ARTIFACT_NAME --output figs/artifact.png # or mesokit interpret explain
```
