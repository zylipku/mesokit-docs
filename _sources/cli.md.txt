# Command-Line Reference

`mesokit` is the console script installed with the package. It mirrors the
pipeline — **produce data → train → index the checkpoint → interpret** — as
four command groups plus `sweep`, which runs the first two stages over a
parameter grid, and keeps two project-local registries so that anything you
generate or train once can be referred to by name afterwards. Two more
groups, `skills` and `agent`, set up a coding agent to drive the same
commands.

```text
mesokit data      avail | list | generate | register | validate | parse
mesokit train
mesokit sweep
mesokit model     list | register
mesokit interpret list | extract | explain
mesokit skills    list | path | install
mesokit agent     init
```

Every command and subcommand accepts `--help`. This page is the complete
reference; the [Quickstart](quickstart.md) is the shortest path through it.

## Conventions

**Plugins.** Every command first imports `./plugins/` — each
`plugins/<name>.py` and `plugins/<name>/` package, names starting with `_`
skipped — so a project's own simulators, models, trainers and artifacts
register themselves and recipes can name their classes. A plugin that fails
to import stops the command with the module and the error.

**Run from the repository root.** The CLI resolves three things relative to
the current working directory:

| What | Where | Used by |
| --- | --- | --- |
| Data recipes | `configs/data/<dyn>/<stem>.yaml` | `data generate` |
| Training recipes | `configs/train/<dyn>/<model>/<stem>.yaml` (falls back to the copy inside the installed package) | `train` |
| Registries | `.mesokit/datasets.json`, `.mesokit/checkpoints.json` | every command that takes a name |

Outputs also land in the working directory: `data/<dyn>/` for generated
HDF5 files, `checkpoints/<dyn>/<run>/` for training runs —
`checkpoints/<dyn>/<experiment>/<run>/` for runs grouped by `--experiment`,
registered as `<experiment>/<run>`. All of these are gitignored.

**Environment.** Prefix commands with `pixi run` (or run inside `pixi shell`)
unless `mesokit` is already on your `PATH`:

```sh
pixi run mesokit data avail
```

**Names versus paths.** Wherever a command takes a dataset (`--data`) it
accepts either a registered name or a path to an HDF5 file; wherever it takes
a checkpoint (`--model` in `interpret`, `--from` in `train`, the `model`
subcommands) it needs a registered name — `<run>` or `<experiment>/<run>`; a
bare run name is accepted when only one experiment holds it. Registries
store **pointers**, never copies, so deleting a file leaves a dangling entry
(`mesokit data list` flags it as `MISSING`; `mesokit model prune` drops
checkpoint entries whose file is gone).

**Automatic versioned names.** When you do not pass `--name`, generated
datasets are registered as `<dyn>_v0`, `<dyn>_v1`, … and trained checkpoints
as `<model>_v0`, `<model>_v1`, … — always the next free slot (free in the
registry and on disk), so repeated runs never overwrite each other. Passing
an explicit `--name` that is already registered, or whose run directory
already holds a checkpoint, is an error unless you add `--force`.

**Quiet by default.** Simulators and trainers print a single overwriting
progress line on stderr; `--verbose` (where offered) restores the underlying
solver's full log.

**Errors and exit codes.** Argument and lookup problems (unknown dynamics,
missing file, name collision, failed validation) are reported as
`Invalid value: …` and exit with status `2`; the offending file or name is
never registered. Unexpected failures inside a simulator or trainer surface
as a Python traceback with status `1`.

**Shell completion.** `mesokit --install-completion` installs completion for
the current shell; `mesokit --show-completion` prints it instead.

## Pipeline at a Glance

```text
configs/data/<dyn>/default.yaml ──► mesokit data generate ──► data/<dyn>/<name>.h5 ──┐
your_solver.h5 ──────────────────► mesokit data register ──────────────────────────────┤
any_format.{npz,nc,pt,…} ────────► mesokit data parse ────► data/parsed/<stem>.h5 ─────┤
                                                                                       ▼
                                                                          .mesokit/datasets.json
                                                                                       │
configs/train/<dyn>/<model>/default.yaml ─────────────────► mesokit train ◄────────────┘
                                                                  │
                                        checkpoints/<dyn>/<run>/{model.pt, config.yaml, history.json, run.json}
                                        checkpoints/<dyn>/<experiment>/<run>/…  + runs.json    (--experiment)
                                                                  │
                                                      .mesokit/checkpoints.json ◄── mesokit model register / sync
                                                                  │          (mesokit model list / show / tag / remove / prune)
                                                       mesokit interpret list / extract ──► figs/*.png

mesokit sweep --param KEY=V1,V2,… [--train-param KEY.PATH=V1,V2,…] = data generate + train per grid point
                                                            ──► checkpoints/<dyn>/<experiment>/{<run>/…, runs.json}
```

## `mesokit data`

Produce or catalog trajectory datasets. The on-disk contract every
subcommand reads or writes is the v1 HDF5 cache described in
[Data Processing](data_processing.md).

### `mesokit data avail`

List the predefined simulator recipes compiled into the package (alias:
`mesokit data available`). This is the catalog of what `data generate` can
run, independent of what has been generated on this machine.

```sh
mesokit data avail
```

```text
DYN                       SIMULATOR
allen_cahn_1d             mesokit.data.allen_cahn.allen_cahn_1d.simulate_allen_cahn_1d
cahn_hilliard_2d          mesokit.data.cahn_hilliard.cahn_hilliard_2d.simulate_cahn_hilliard_2d
ising_2d                  mesokit.data.ising.ising_2d.simulate_ising_2d
kdv_1d                    mesokit.data.kdv.kdv_1d.simulate_kdv_1d
llg_lattice_2d            mesokit.data.llg.llg_lattice_2d.simulate_llg_lattice_2d
peridynamics_fracture_2d  mesokit.data.peridynamics.peridynamics_fracture_2d.simulate_peridynamics_fracture_2d
```

The `SIMULATOR` column is the Python callable each recipe dispatches to; the
physics, numerical scheme and parameters of every entry are documented in
[Predefined Datasets](data_processing/predefined.md).

### `mesokit data list`

List the datasets registered in `.mesokit/datasets.json`, grouped by
dynamics. A dataset whose `dyn` attribute matches a predefined simulator is
listed under that name; anything else lands in a trailing `custom:` group.
The second column says whether the file still exists (`yes`) or the registry
points at something that has been moved or deleted (`MISSING`).

```sh
mesokit data list
```

```text
allen_cahn_1d:
  allen_cahn_1d_v0  yes  /home/me/mesokit/data/allen_cahn_1d/allen_cahn_1d_v0.h5
  ac_eps05          yes  /home/me/mesokit/data/allen_cahn_1d/ac_eps05.h5

kdv_1d:
  kdv_1d_v0         yes  /home/me/mesokit/data/kdv_1d/kdv_1d_v0.h5

custom:
  md_slab           MISSING  /scratch/md/slab_density.h5
```

With nothing registered it prints `(no datasets)`.

### `mesokit data generate`

Run a predefined simulator from a recipe, write the trajectories to HDF5,
validate the file and register it.

```sh
mesokit data generate --dyn DYN [--config STEM] [--name NAME | --no-registry]
                      [--output PATH] [--force] [--verbose] [--set KEY=VALUE ...]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--dyn DYN` | required | Predefined dynamics name (one of `mesokit data avail`). |
| `--config STEM\|PATH` | `default` | Recipe `configs/data/DYN/STEM.yaml` (working directory, then the installed package), or a path to any YAML file. |
| `--name NAME` | `DYN_v<n>` | Registry name for the result. |
| `--no-registry` | off | Write the file but do not register it. Mutually exclusive with `--name`. |
| `--output PATH` | `data/DYN/<name>.h5` | Where to write the HDF5 file. Parent directories are created. |
| `--force` | off | Replace an existing registry entry of the same name. |
| `--verbose` | off | Show the solver's own per-step output instead of the progress line. |
| `--set KEY=VALUE` | none | Override one recipe key for this run; repeatable. `KEY` must be a keyword argument of the simulator; `VALUE` is read as int, float, bool (`true` / `false`) or string, in that order. |

What happens, in order: the recipe is loaded with Hydra, the `--set`
overrides are merged on top (an unknown key is rejected before anything
runs), and the result is instantiated (every key in the YAML is a keyword
argument of the simulator, and `verbose` is forwarded); the returned
`TrajectoryDataset` is saved; the saved file is run through the same
validator as `data register`; on success the registry entry is written and
the validation summary is printed.

```sh
mesokit data generate --dyn allen_cahn_1d --config fdr --name ac_smoke
```

```text
allen_cahn_1d: 10/10 trajectories
wrote data/allen_cahn_1d/ac_smoke.h5: shape=(10, 101, 1, 256)
registered 'ac_smoke' -> /home/me/mesokit/data/allen_cahn_1d/ac_smoke.h5
dyn=allen_cahn_1d
n_traj=10
n_time=101
n_channel=1
grid_shape=(256,)
data_dtype=float32
dt=0.001
channel_names=('u',)
physical: {'Lx': 6.283185307179586, 'T': 0.1, 'eps': 0.1}
numerical: {'Nk': 3, 'Nx': 256, 'T_save_steps': 25, 'dealias': 2, 'dt': 4e-05, 'dx': 0.02454369260617026, 'max_k': 10}
provenance: {'seed': 0, 'u_bound': 10.0}
```

More examples:

```sh
# The reference dataset, auto-named allen_cahn_1d_v0 (then _v1, _v2, … on repeats).
mesokit data generate --dyn allen_cahn_1d

# A variant recipe: configs/data/ising_2d/kac.yaml (Kac interaction).
mesokit data generate --dyn ising_2d --config kac --name ising_kac_T07

# Write somewhere else and keep it out of the registry (scratch experiments).
mesokit data generate --dyn cahn_hilliard_2d --config fdr --output /tmp/ch_test.h5 --no-registry

# Re-run a recipe you changed and replace the previous entry of the same name.
mesokit data generate --dyn kdv_1d --name kdv_long --force

# Watch Dedalus's per-step log instead of the progress line.
mesokit data generate --dyn kdv_1d --config fdr --verbose

# One-off parameter change without a new recipe file.
mesokit data generate --dyn allen_cahn_1d --set eps=0.05 --set seed=1 --name ac_eps0.05_s1
```

To change parameters for good, add a sibling YAML under `configs/data/<dyn>/`
(copy `default.yaml`, edit, pick it with `--config`); for a one-off run use
`--set`, and for a whole grid of values use [`mesokit sweep`](#mesokit-sweep).
Every predefined recipe also ships `fdr.yaml`, a seconds-long "fast dev run"
for trying the pipeline.
Some recipes are heavy — the default `cahn_hilliard_2d` takes about ten
minutes and `peridynamics_fracture_2d` about twenty-five; the per-dataset
sections of [Predefined Datasets](data_processing/predefined.md) give sizes
and timings.

Errors you may see:

```text
Invalid value: config dir not found: /home/me/mesokit/configs/data/nope
Invalid value: no config 'nope' under /home/me/mesokit/configs/data/allen_cahn_1d; available: default, fdr
Invalid value: --name and --no-registry are mutually exclusive
Invalid value: dataset 'ac_smoke' already registered; pass --force to overwrite
Invalid value: expected KEY=VALUE, got 'eps'
Invalid value: unknown parameter 'epsilon' for simulator mesokit.data.allen_cahn.allen_cahn_1d.simulate_allen_cahn_1d; accepted: eps, n_traj, Nx, Lx, T, T_save_steps, timestep, Nk, max_k, u_bound, dealias, seed, verbose
```

The first one also appears when you run from the wrong directory: recipes
are looked up in `./configs/data/`, not inside the package.

### `mesokit data register`

Validate an HDF5 file you produced yourself against the v1 cache contract
and register it under a name.

```sh
mesokit data register --name NAME --file FILE.h5 [--force]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--name NAME` | required | Registry name. |
| `--file FILE` | required | Existing HDF5 file; the absolute path is stored. |
| `--force` | off | Replace an existing entry of the same name. |

The validator checks the closed set of root attributes, the `data` /
`times` datasets and their shapes and dtypes, finiteness, monotone times,
the three metadata groups and the optional `channel_names`. On success it
prints the inferred summary shown above for `data generate`; on failure
each failing check is printed and nothing is registered.

```sh
mesokit data register --name md_slab --file /scratch/md/slab_density.h5
```

```text
registered 'md_slab' -> /scratch/md/slab_density.h5
dyn=binary_lj_slab
n_traj=3
n_time=2001
n_channel=1
grid_shape=(50, 50, 200)
data_dtype=float32
dt=1
channel_names=('x_A',)
physical: {'T': 1.1, 'xA': 0.5, 'Lx': 9.52, 'Ly': 9.52, 'Lz': 38.1}
numerical: {'dx': 0.19, 'sigma_kde': 1.5}
provenance: {'source': 'lammps', 'seed': 42}
```

A file that is not a v1 cache fails like this:

```text
  cannot open /tmp/bad.h5 as HDF5: Unable to synchronously open file (file signature not found)
Invalid value: sanity check failed for /tmp/bad.h5; not registered
```

Writing a conforming file is a few lines of `h5py`; see
[Custom Datasets](data_processing/custom.md). To check a file without
registering it, use `mesokit data validate` below (or the Python helper
`mesokit.data.validate(path)`).

### `mesokit data validate`

Check a file against the v1 contract and print the inferred metadata,
without touching the registry. `register` runs the same check before it
writes an entry, and the agent behind `parse` runs it on its own output.

```sh
mesokit data validate FILE
```

```text
validated /scratch/md/slab_density.h5
dyn=binary_lj_slab
n_traj=3
…
```

A non-conforming file prints each failing check and exits with status `2`:

```text
  cannot open /tmp/bad.h5 as HDF5: Unable to synchronously open file (file signature not found)
Invalid value: validation failed for /tmp/bad.h5
```

### `mesokit data parse`

Hand an arbitrary dataset to a coding agent installed on your machine, let
it convert the file with the `mesokit-convert-data` skill shipped in the
package, then validate (and optionally register) the result. The skill
itself, and the five others that cover training and extending, are
described in [Agent Skills](skills.md); `mesokit skills` below installs
them into an agent for conversational use.

```sh
mesokit data parse --file FILE [--output PATH] [--hint TEXT]
                   [--agent claude|codex] [--backend foreground|tmux]
                   [--agent-args "FLAGS"] [--name NAME] [--force]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--file FILE` | required | Input in any format (`.npz`, `.npy`, `.nc`, `.pt`, non-conforming `.h5`, …). It may live outside the working directory. |
| `--output PATH` | `data/parsed/<stem>.h5` | Where the agent must write the v1 file. Must not exist yet, unless `--force` is given. |
| `--hint TEXT` | none | Free-form instructions appended to the agent's prompt (axis names, units, which variable is the field, …). |
| `--agent` | `claude` | Agent CLI: `claude` (runs `claude -p …`) or `codex` (runs `codex exec …`). Checked first: if the command is not installed, `parse` stops and prints the official installation guide to follow. |
| `--backend` | `foreground` | `foreground` blocks and streams the agent's output; `tmux` detaches into a session. |
| `--agent-args "FLAGS"` | none | Extra flags for the agent command, split like a shell and appended after the built-in ones: `"--model opus"`, `"--allowedTools Bash(uv run:*)"`, `"-c model=o3"`. |
| `--name NAME` | none | Register the produced file under this name on success. Without it the file is only validated. |
| `--force` | off | Replace an existing output file, and an existing registry entry of the same name. |

Before anything is created or launched, the command checks that the
agent's CLI (`claude` or `codex`) is installed in the shell it runs in. If
it is not, it exits at once and names the official installation guide:
[Claude Code](https://code.claude.com/docs/en/setup) or the
[Codex CLI](https://developers.openai.com/codex/cli). Install the agent
there, confirm `claude --version` (or `codex --version`) works, and re-run.

**What the agent may do.** The agent runs non-interactively (`claude -p`,
`codex exec`), so nothing can be approved once it has started: `parse`
grants what a conversion needs on the command line, no more, and prints
that command line (the `argv` line below) so the grants are visible. It
works from any directory, a plain folder that is not a git checkout
included; the agent's working directory is the one you run `mesokit` in.

- `claude`: `--permission-mode acceptEdits`, which auto-approves file
  writes inside the working directory and nothing else; `--allowedTools`
  listing the Bash commands `python`, `python3`, the interpreter `mesokit`
  itself runs in, `mesokit` and `pixi run`; and `--add-dir` for the input's
  and the output's directories when they lie outside the working
  directory. Neither `--dangerously-skip-permissions` nor
  `bypassPermissions` is used.
- `codex`: the `workspace-write` sandbox (commands may write under the
  working directory and read anywhere; no network), set as
  `-c sandbox_mode=workspace-write` so that a `--sandbox` given through
  `--agent-args` overrides it; `--add-dir` for an output directory outside
  the working directory; and `--skip-git-repo-check`.

For both, stdin is closed (`/dev/null`; each CLI would otherwise read a
piped stdin as more prompt). A different model, a wider allowlist or
another sandbox go through `--agent-args`, for example
`--agent-args "--sandbox danger-full-access"` on a machine where Codex's
bubblewrap sandbox cannot start.

**The prompt.** The skill's text is embedded in the prompt — nothing
outside the project has to be readable — together with the input and
output paths, the interpreter to use (the one `mesokit` runs in, so a
`pipx` install works too), the self-check
`<python> -m mesokit data validate <output>` to repeat until it passes,
and your `--hint`. The agent is told not to register anything; `parse`
does that itself on return.

**On return.** In the foreground backend the command returns when the
agent exits. A non-zero exit, or an output file the agent did not write,
is an error. A file that already sits at the output path is refused before
the agent is launched (with `--force` it is removed first), so what gets
validated is always the agent's own work.

```sh
mesokit data parse --file ~/runs/burgers.npz \
  --hint "arrays u (traj, time, x) and t; domain is [0, 2π) periodic; call it burgers_1d" \
  --name burgers_v0
```

```text
launching agent 'claude' via backend 'foreground'
  skill : /home/me/.venv/lib/python3.12/site-packages/mesokit/skills/mesokit_convert_data/SKILL.md (embedded in the prompt)
  input : /home/me/runs/burgers.npz
  output: /home/me/project/data/parsed/burgers.h5
  argv  : claude -p --permission-mode acceptEdits --allowedTools 'Bash(python:*),…' --add-dir /home/me/runs -- <prompt>
… agent transcript …
registered 'burgers_v0' -> /home/me/project/data/parsed/burgers.h5
dyn=burgers_1d
…
```

With `--backend tmux` the command returns immediately and tells you how to
follow up:

```text
agent launched detached (handle: mesokit-parse-1756800000)
  attach: tmux attach -t mesokit-parse-1756800000
when the agent finishes, validate / register with:
  mesokit data register --name burgers_v0 --file /home/me/mesokit/data/parsed/burgers.h5
```

Errors: `agent 'claude' is not installed` (with the official installation
guide to follow), `unknown agent 'x'; available: claude, codex`, `backend 'tmux' requires the tmux binary on
PATH`, `output <path> already exists; pass --force to replace it, or
--output for another path`, `agent exited with code N`, `agent finished
but <output> was not written`.

## `mesokit train`

Train a registered model architecture on a dataset through the trainer
registered for that model, write a run directory, and index the checkpoint.

```sh
mesokit train --model ARCH --data NAME_OR_PATH [--dyn DYN]
              [--config STEM|PATH] [--set KEY=VALUE ...] [--trainer NAME]
              [--experiment E] [--name NAME | --no-registry] [--from CKPT]
              [--tag T ...] [--notes TEXT] [--force]
              [--epochs N] [--batch-size N] [--device auto|cpu|gpu]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--model ARCH` | required (or from `--from`) | Architecture name from the model registry (`fno1d`, `spectral_onsagernet_1d`, …). |
| `--data` | required (or from `--from`) | Registered dataset name **or** path to a v1 HDF5 file. |
| `--dyn DYN` | the dataset's `dyn` | Dynamics name; selects the recipe tree `configs/train/DYN/ARCH/` and the run directory `checkpoints/DYN/`. |
| `--config STEM\|PATH` | `default` | Recipe `configs/train/DYN/ARCH/STEM.yaml`, looked up in the working directory first, then in the installed package (then a checkout); or a path to any YAML file. With no recipe directory at all, built-in defaults are used. |
| `--set KEY=VALUE` | none | Change one recipe key for this run (`trainer.lr=1e-4`, `model.potential.eps=0.05`, `dataset.stride=2`); repeatable. Values are parsed as YAML. |
| `--trainer NAME` | `= --model` | Trainer registry name; every shipped model registers its own default. |
| `--experiment E` | none | Group the run: it lands in `checkpoints/DYN/E/<run>/`, is registered as `E/<run>`, and `E/runs.json` gets a row (see [Experiments](#experiments) below). |
| `--name NAME` | `ARCH_v<n>`; in an experiment `ARCH_<key><value>…` from `--set`, else `ARCH_r<nn>` | Run name: the registry key and the run directory. `--name E/NAME` is `--experiment E --name NAME`. |
| `--from CKPT` | none | Continue from a registered checkpoint: its weights are loaded into the new model, its saved `config.yaml` is the recipe (unless `--config`), and its dataset, model, trainer and dyn fill in whatever is not given; `--set` applies on top. The new record says `from: CKPT`. |
| `--no-registry` | off | Train and write the run directory but do not index it. |
| `--tag T` | none | Tag recorded on the run (`run.json` and the registry); repeatable. `mesokit model list --tag T` filters on it. |
| `--notes TEXT` | empty | Free-text note recorded on the run. |
| `--force` | off | Replace an existing checkpoint entry of the same name and reuse its run directory (stale Lightning `.ckpt` files are cleared first). |

The model's grid is read from the dataset: any of `Nx` / `Ny` / `Nz`,
`Lx` / `Ly` / `Lz`, `grid_shape`, `domain` and `in_dim` that the model (or
a nested potential / block) accepts and the recipe leaves out is filled
from the dataset's `grid_shape` and `physical` box lengths (`2π` when
absent). A box length written in the recipe or passed with `--set` is
kept; a written `Nx` / `grid_shape` / `in_dim` that contradicts the
dataset is refused before training, naming the key. The shipped recipes
carry no grid keys. The saved `config.yaml` records the completed
configuration.
| `--epochs N` | from config | Override `trainer.max_epochs`. |
| `--batch-size N` | from config | Override `dataloader.batch_size`. |
| `--device` | from config | Override `trainer.accelerator`: `auto`, `cpu` or `gpu`. |

A training recipe has four sections — `model` (constructor kwargs),
`dataset` (which `torch.utils.data.Dataset` view of the trajectories to
train on, e.g. `SnapshotPairDataset` with a `stride`), `dataloader`, and
`trainer` (epochs, optimiser, scheduler, accelerator, rollout steps, …).
If the recipe leaves `trainer.dt` unset, the step is taken from the
dataset's `numerical/dt` attribute, or else from the spacing of `times`.
The name collision check runs **before** training starts, so a duplicate
`--name` fails fast.

```sh
mesokit train --model spectral_onsagernet_1d --dyn allen_cahn_1d --data allen_cahn_1d_v0 \
  --epochs 20 --device cpu
```

```text
… Lightning progress …
trained 'spectral_onsagernet_1d' with 'spectral_onsagernet_1d'
  checkpoint: /home/me/mesokit/checkpoints/allen_cahn_1d/spectral_onsagernet_1d_v0/model.pt
  config:     /home/me/mesokit/checkpoints/allen_cahn_1d/spectral_onsagernet_1d_v0/config.yaml
  metrics:    train_loss=0.0004203 epochs=20 time=10.1s
  registered: spectral_onsagernet_1d_v0
```

The run directory contains:

| File | Contents |
| --- | --- |
| `model.pt` | Plain `state_dict` — loadable with `torch.load` + `model.load_state_dict`, no Lightning needed. The canonical artifact. |
| `config.yaml` | The fully resolved recipe plus `model_name`, `trainer_name`, `dyn`, `data`, `dataset_name`, `checkpoint_name`, `train_config`. This is what `mesokit interpret` reads to rebuild the model. |
| `history.json` | Per-epoch metric series, e.g. `{"train_loss": [...]}`. |
| `run.json` | The run's record: `name`, `created`, `status`, the `dyn` / `model_name` / `trainer_name`, the dataset (`data`, `dataset_name` and the resolved `dataset_path`), the `recipe` (`spec`, `source`, `path`), the `--set` list as `overrides` and the same keys with parsed values as `params`, the `cli` knobs (`epochs`, `batch_size`, `device`), the final `metrics` (`train_loss`, `train_loss_min`, `val_loss`, `epochs_run`, `wall_time_s`), `tags`, `notes` and the config hash. The registry entry is this record plus the paths; `mesokit model list` reads the entries. A run that raises inside the trainer leaves `run.json` with `status: failed` and the error, so `mesokit model prune` can find it. |
| `last.ckpt`, `lit_epoch=NNN.ckpt` | Lightning checkpoints (optimizer state etc.) written by `LitTrainer`; not needed downstream. |

More examples:

```sh
# Train on a file that was never registered (registry name stays empty in the record).
mesokit train --model fno1d --dyn kdv_1d --data /tmp/kdv_scratch.h5 --config default --epochs 5

# Give the run a meaningful name and overwrite a previous attempt.
mesokit train --model spectral_onsagernet_1d --dyn allen_cahn_1d --data ac_eps05 \
  --name son_eps05_long --epochs 200 --force

# A hyper-parameter variant: copy default.yaml to configs/train/allen_cahn_1d/spectral_onsagernet_1d/lr1e-4.yaml, then
mesokit train --model spectral_onsagernet_1d --dyn allen_cahn_1d --data allen_cahn_1d_v0 --config lr1e-4

# Throw-away run that must not pollute the checkpoint index (`mesokit model prune` deletes such run directories).
mesokit train --model fno1d --dyn allen_cahn_1d --data allen_cahn_1d_v0 --epochs 1 --device cpu --no-registry

# Tag runs so `mesokit model list --tag paper` finds them later.
mesokit train --model spectral_onsagernet_1d --data allen_cahn_1d_v0 --set trainer.lr=1e-4 --tag paper --notes "lr scan, best"

# Three learning rates side by side, under one experiment: checkpoints/allen_cahn_1d/lr-scan/{…_lr0.001, …_lr0.0001, …_lr1e-05}/
for lr in 1e-3 1e-4 1e-5; do
  mesokit train --model spectral_onsagernet_1d --data allen_cahn_1d_v0 --experiment lr-scan --set trainer.lr=$lr --epochs 20
done
mesokit model list --experiment lr-scan --sort train_loss

# Keep training the best one for 200 more epochs, at a lower rate.
mesokit train --from lr-scan/spectral_onsagernet_1d_lr0.0001 --name lr-scan/son_long --epochs 200 --set trainer.lr=3e-5
```

(experiments)=

### Experiments

`--experiment E` (on `train`, and always on `sweep`) adds one grouping
level to the run layout:

```text
checkpoints/<dyn>/
├── <run>/                       # runs without --experiment: model.pt, config.yaml, history.json, run.json, *.ckpt
└── <experiment>/
    ├── runs.json                # the experiment's table: one row per run, failed ones included
    └── <run>/                   # the same files as a flat run
```

The registry key mirrors the path, `<experiment>/<run>`, so `ls`, `rm -r`
and `du` group what the CLI groups; a bare `<run>` is accepted by every
command that takes a name as long as only one experiment holds it. The
default run name inside an experiment says what varied —
`<model>_<key><value>[_…]` from the `--set` keys' last components
(`spectral_onsagernet_1d_lr0.0001`), `<model>_r<nn>` when nothing was
overridden; a taken name gets `_2`, `_3`, … unless `--force`, which reuses
it. A run name cannot be an existing experiment's and vice versa.

`runs.json` is the experiment's log (`schema_version`, `experiment`, `dyn`,
`model`, `created`, `updated`, the training `axes` and simulator
`data_axes` seen so far, and `rows`); every `train --experiment E` inserts or
replaces its row, so does every point of a `sweep`. A row holds `run`,
`checkpoint` (the registry key), `dataset`, `dataset_path`,
`checkpoint_path`, `status`, `data_status` (`generated`, `reused` or
`given`), `params`, `data_params`, `metrics`, `wall_time_s`, `error` and
`created`; a point that failed has a row but no run directory or registry
entry. `mesokit model sync` rebuilds the table from the run directories.

Two things to know:

- The shipped `smoke.yaml` under `configs/train/allen_cahn_1d/spectral_onsagernet_1d/`
  is a test fixture with `Nx: 8`; it does not fit the 256-point datasets.
  For a quick real run use `--config default --epochs 1 --device cpu`.
- Every shipped architecture is registered once per dimension — `fno1d` /
  `fno2d` / `fno3d`, `spectral_onsagernet_1d` / `_2d` / `_3d` and
  `onsagernet_1d` / `_2d` / `_3d` — pick the suffix that matches the
  dataset's grid. What the model sees of a multi-channel dataset
  (`llg_lattice_2d`, `peridynamics_fracture_2d`) is the recipe's
  `dataset.channel` key: an integer for one field, `null` for every
  channel, a list for some; the model's channel count follows
  ([Models](models.md)). A model (or trainer) of your own under `./plugins/` is imported
  before every command, so its registered name works like a shipped one
  (a model without a trainer of its own trains with `LitTrainer`); a recipe
  may also name any class by `model._target_` / `trainer._target_`. See
  [Custom Models](models/custom_model.md).

Errors:

```text
Invalid value: dataset 'nope' is not registered and is not an existing HDF5 path
Invalid value: registered dataset 'old' points to missing file: /home/me/mesokit/data/allen_cahn_1d/old.h5
Invalid value: no config 'nope' under /home/me/mesokit/configs/train/allen_cahn_1d/spectral_onsagernet_1d; available: default, smoke
Invalid value: --device must be one of: auto, cpu, gpu
Invalid value: checkpoint 'spectral_onsagernet_1d_v0' already registered; pass --force to overwrite
Invalid value: run directory checkpoints/allen_cahn_1d/son_a already holds a checkpoint; pass --force to overwrite it or choose another --name
```

(mesokit-sweep)=

## `mesokit sweep`

Train one checkpoint per point of a parameter grid, as one experiment. Two
kinds of axis combine: `--param` varies a **simulator** parameter (one
dataset is generated per value, as `data generate --set` would), and
`--train-param` varies a **training-recipe** key such as `trainer.lr`
(several checkpoints on the same dataset, as `train --set` would). The runs
land under `checkpoints/<dyn>/<experiment>/`, the table is that experiment's
`runs.json`. This is the built-in form of the "for eps in …" shell loop.

```sh
mesokit sweep --dyn DYN --model ARCH [--param KEY=V1,V2,... ...] [--train-param KEY.PATH=V1,V2,... ...]
              [--data NAME_OR_PATH] [--experiment E] [--tag T ...]
              [--data-config STEM] [--config STEM] [--trainer NAME] [--name-prefix PREFIX]
              [--epochs N] [--batch-size N] [--device auto|cpu|gpu]
              [--reuse-data] [--force] [--dry-run]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--dyn DYN` | required | Dynamics name; selects `configs/data/DYN/` and `configs/train/DYN/ARCH/`. |
| `--model ARCH` | required | Architecture name from the model registry. |
| `--param KEY=V1,V2,...` | repeatable | A data axis. `KEY` is a keyword argument of the simulator (as for `data generate --set`); each value is read as int, float, bool or string. |
| `--train-param KEY.PATH=V1,V2,...` | repeatable | A training axis over a recipe key (`trainer.lr`, `model.n_modes`, `dataset.stride`); values as above. At least one axis of either kind is required; all axes form one Cartesian product, data axes outermost. |
| `--data NAME_OR_PATH` | none | The dataset every point trains on, when there is no `--param` axis (required then, refused otherwise). |
| `--experiment E` | `ARCH_<axes>_<timestamp>` | The experiment the runs are grouped under. |
| `--tag T` | none | Tag recorded on every run; repeatable. |
| `--data-config STEM` | `default` | Data recipe `configs/data/DYN/STEM.yaml` the overrides are applied to. |
| `--config STEM` | `default` | Training recipe `configs/train/DYN/ARCH/STEM.yaml`. |
| `--trainer NAME` | `= --model` | Trainer registry name. |
| `--name-prefix PREFIX` | `DYN` | Prefix of every generated dataset name (see below). |
| `--epochs N`, `--batch-size N`, `--device` | from config | Forwarded to every training run, as for `train`. |
| `--reuse-data` | off | Skip generation for a point whose dataset name is already registered and whose file exists; train on it instead. |
| `--force` | off | Replace existing dataset and checkpoint entries of the same names. |
| `--dry-run` | off | Print the plan — names and overrides per point — and exit without running anything. |

**Names.** A data point `eps=0.05, T=0.5` gives the dataset
`<prefix>_eps0.05_T0.5`; a run is named `<model>_<key><value>[_…]` over both
kinds of axis, training keys by their last component (`eps=0.05,
trainer.lr=1e-3` → `spectral_onsagernet_1d_eps0.05_lr0.001`), and registered
as `<experiment>/<run>`. Floats are written compactly: `1.0` becomes `1`,
`2e-5` becomes `2e-05`. The names are deterministic, so re-running the same
sweep with `--experiment E --reuse-data --force` retrains on the existing
data and replaces the rows. A dataset is generated once per data point and
shared by that point's training runs (`reused` in the table).

**Failures.** Every point runs to the end of the grid: a point whose
simulator or trainer raises is marked `FAILED` in the table with the error
message, the remaining points still run, and the command exits with status
`1` at the end. Problems that would break every point — a missing recipe, a
parameter the simulator does not accept — are reported before anything runs.

```sh
mesokit sweep --dyn allen_cahn_1d --model spectral_onsagernet_1d --param eps=0.05,0.1,0.2 \
  --experiment eps-scan --data-config fdr --epochs 2 --device cpu
```

```text

[1/3] eps=0.05

  training checkpoint 'eps-scan/spectral_onsagernet_1d_eps0.05'
```

```python
pd.DataFrame(rows)[["data_params", "checkpoint", "metrics", "status"]]
```

which returns the list of row dicts.

```sh
mesokit model list --experiment lr-scan --sort train_loss

# Data axes times training axes: 2 datasets, 4 checkpoints; see the names before committing to the runs.
mesokit sweep --dyn allen_cahn_1d --model spectral_onsagernet_1d \
  --param eps=0.05,0.1 --train-param trainer.lr=1e-3,1e-4 --dry-run

# Retrain a grid whose datasets already exist, replacing the old checkpoints and rows.
mesokit sweep --dyn allen_cahn_1d --model fno1d --param eps=0.05,0.1,0.2 \
  --experiment eps-scan --reuse-data --force --epochs 50

# Custom prefix, variant training recipe.
mesokit sweep --dyn ising_2d --model spectral_onsagernet_2d --param T=1.5,2.0,2.5 \
  --data-config kac --name-prefix ising_kac --config default --epochs 20
```

## `mesokit model`

Manage the project-local index of **trained checkpoints**
(`.mesokit/checkpoints.json`). This is not the registry of architectures —
that one is populated by the package and inspected from Python with
`mesokit.models.available()`.

Every entry mirrors the run's `run.json` (see [`mesokit train`](#mesokit-train)):
the model, dataset and recipe it came from, the `--set` overrides as
`params`, the final `metrics`, `created`, `tags` and `notes`, plus the paths.
Entries written by earlier versions (schema 1: paths and names only) are
read as they are, with empty `params` / `metrics`, and the file is stamped
schema 2 on its next write.

### `mesokit model list`

```sh
mesokit model list [--dyn D] [--model ARCH] [--experiment E] [--dataset NAME] [--tag T ...]
                   [--sort COLUMN] [--reverse] [--format table|json|csv] [--columns a,b,...]
```

```text
NAME                                   MODEL                   DATASET           PARAMS             TRAIN_LOSS  EPOCHS  TIME   CREATED              TAGS
lr-scan/spectral_onsagernet_1d_lr0.0001  spectral_onsagernet_1d  allen_cahn_1d_v0  trainer.lr=0.0001  0.0003117   20      10.3s  2026-09-08T10:21:40  -
lr-scan/spectral_onsagernet_1d_lr0.001   spectral_onsagernet_1d  allen_cahn_1d_v0  trainer.lr=0.001   0.0004203   20      10.1s  2026-09-08T10:15:02  -
son_eps05_long                         spectral_onsagernet_1d  ac_eps05          -                  0.0002950   200     97.4s  2026-09-08T09:12:40  paper
```

| Option | Meaning |
| --- | --- |
| `--dyn`, `--model`, `--experiment`, `--dataset`, `--tag` | Keep only the matching runs (`--experiment -` keeps the runs outside any experiment; `--tag` is repeatable and every given tag must be present). |
| `--sort COLUMN` | Any column name (`name`, `created`, `train_loss`, `train_loss_min`, `val_loss`, `epochs`, `time`, `model`, `dataset`, …); runs without a value sort last. `--reverse` descends. |
| `--format` | `table` (default), `json` (the full records as one list, for `pandas.DataFrame`) or `csv` (the selected columns). |
| `--columns` | Comma-separated columns; the default is `name,model,dataset,params,train_loss,epochs,time,created,tags`. Also available: `experiment`, `run`, `dyn`, `trainer`, `data_params`, `train_loss_min`, `val_loss`, `status`, `notes`, `recipe`, `path`, `config`. |

`PARAMS` are the recipe keys the run changed with `--set` or a sweep's
`--train-param` (a sweep's simulator axes are `data_params`); `TRAIN_LOSS`
is the last epoch's training loss (`-` when the trainer logs none, and for
entries made by `model register`). Rows are sorted by name unless `--sort`
says otherwise; with nothing registered it prints `(no checkpoints registered)`.

### `mesokit model register`

Index a checkpoint that was trained elsewhere (a notebook, a cluster job,
another machine). Only pointers are stored; nothing is copied.

```sh
mesokit model register --model NAME --file CKPT.pt --config CONFIG.yaml [--tag T ...] [--force]
```

| Option | Meaning |
| --- | --- |
| `--model NAME` | Registry name (required). |
| `--file CKPT.pt` | Existing checkpoint file: a `state_dict`, or a dict with a `state_dict` key such as a Lightning checkpoint (required). |
| `--config CONFIG.yaml` | The recipe used to train it; must contain a `model` section with a `_target_` so `interpret` can rebuild the architecture (required). `model_name`, `dyn` and `dataset_name` are copied from it into the entry when present, so the `list` columns are filled. |
| `--tag T` | Tag recorded on the entry; repeatable. |
| `--force` | Replace an existing entry. |

```sh
mesokit model register --model son_cluster_run --file ~/jobs/1234/model.pt --config ~/jobs/1234/config.yaml
```

```text
registered 'son_cluster_run'
  checkpoint: /home/me/jobs/1234/model.pt
  config:     /home/me/jobs/1234/config.yaml
```

The simplest way to obtain a valid pair is to train once with
`mesokit train` (even with `--no-registry`) and copy its `config.yaml`
alongside your own checkpoint. When loading, `interpret` strips a leading
`model.` prefix and any `._orig_mod.` (from `torch.compile`) from the
parameter names, so Lightning-style checkpoints load unchanged.

### `mesokit model tag`

```sh
mesokit model tag NAME [--add T ...] [--remove T ...] [--notes TEXT]
```

Adds or drops tags on a run, or rewrites its notes; the registry entry and
the run's `run.json` are both updated (`mesokit train --tag` sets tags at
training time).

### `mesokit model remove`

```sh
mesokit model remove NAME [--delete-files]
```

Drops the entry. With `--delete-files` the run directory `mesokit train`
wrote is deleted as well; an entry made by `model register` has no run
directory of its own, so its files are left where they are.

### `mesokit model prune`

```sh
mesokit model prune [--dry-run]
```

Reconciles the index with the disk: entries whose `model.pt` is gone are
dropped, and run directories under `checkpoints/<dyn>/` (flat or inside an
experiment) that hold no registered checkpoint — a `--no-registry` smoke
run, a run whose entry was removed, a run that failed inside the trainer and
left no `model.pt` — are deleted. Only directories holding a run's files
(`run.json`, `model.pt`, `config.yaml`, `history.json`, `*.ckpt`) are ever
touched, and `runs.json` keeps its rows; `--dry-run` prints the plan and
changes nothing.

```text
would remove entry 'son_old': checkpoint missing (/home/me/mesokit/checkpoints/allen_cahn_1d/son_old/model.pt)
would remove run directory /home/me/mesokit/checkpoints/allen_cahn_1d/spectral_onsagernet_1d_v4 (not registered)
would remove run directory /home/me/mesokit/checkpoints/allen_cahn_1d/son_crashed (no model.pt)
```

### `mesokit model sync`

```sh
mesokit model sync [--import-sweeps]
```

Rebuilds the index from the run directories: every completed run (a
`run.json` with `status: ok` next to a `model.pt`) gets an entry keyed by
its location — `<run>` or `<experiment>/<run>` — with the paths as found,
so a project directory that was moved, a run directory moved into an
experiment folder by hand, or an index that was deleted is put back
together. Registered runs from before `run.json` existed get one written,
with `metrics` read from `history.json` and `created` from `model.pt`'s
modification time; each experiment's `runs.json` is reconciled with its run
directories (failed rows are kept). Entries without a run directory
(`model register`) are left alone. `--import-sweeps` also reads the legacy
`checkpoints/<dyn>/sweeps/*.json` summaries into the matching entries
(`data_params`, `train_loss`, a `sweep:<stamp>` tag).

```text
synced 12 entries: 3 added, 1 updated, 4 backfilled from history.json, 2 experiment table(s) refreshed
```

## `mesokit interpret`

Inspect the interpretability artifacts a trained checkpoint can produce.
Every registered model implements `list_artifacts()` and `artifact(name)`;
these commands are thin wrappers that rebuild the model from its registry
record, load the weights, and call them.

`--model` takes the registry key (`<run>` or `<experiment>/<run>`; a bare
run name when only one experiment holds it). Data-backed artifacts read the
dataset the checkpoint was trained on: the file recorded in its run record
(`dataset_path`) while it exists — a dataset re-registered under the same
name since then is reported and not used — else the dataset's current
registry entry, as for checkpoints from earlier versions.

How a checkpoint is rebuilt: the registry record gives `config_path`; the
`model` section of that YAML is instantiated; `model.pt` is loaded as a
`state_dict` (strictly — every parameter must match); the model is put in
`eval()` mode. For `extract`, the dataset the checkpoint was trained on is
located too (by its registered name, else by the path recorded in the
config) and handed to the model as reference data for artifacts that need
snapshots (a learned potential is evaluated along real states, for
instance).

### `mesokit interpret list`

```sh
mesokit interpret list --model CKPT_NAME
```

```text
spectral_onsagernet_1d_v0:
  potential
```

FNO checkpoints list `spectrum`, the per-mode response / one-step error
diagnostics described in [Fourier Neural Operator](models/fno.md);
it needs the checkpoint's dataset for the grid and the error spectrum.

### `mesokit interpret extract`

Build one artifact (or all of them), print its one-paragraph summary, and
save its figure. `mesokit interpret explain` is an exact alias.

```sh
mesokit interpret extract --model CKPT_NAME --artifact NAME --output FILE.png [--max-snapshots N]
mesokit interpret extract --model CKPT_NAME --artifact all  --output DIR/     [--max-snapshots N]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--model` | required | Registered checkpoint name. |
| `--artifact` | required | An entry from `interpret list`, or `all` (also `*`). |
| `--output` | required | Target file; the extension selects the matplotlib format (`.png`, `.pdf`, `.svg`, …). With `--artifact all` it must be a directory — a path with an extension is rejected — and one PNG per artifact, named `<model>_<artifact>.png`, is written inside it. |
| `--max-snapshots N` | `5000` | Cap on the number of reference snapshots handed to data-backed artifacts. Lower it to speed up extraction on large datasets. |

```sh
mesokit interpret extract --model spectral_onsagernet_1d_v0 --artifact potential --output figs/potential.png
```

```text

saved: /home/me/mesokit/figs/potential.png
```

## `mesokit skills`

The agent skills shipped in the package (`mesokit-convert-data`,
`mesokit-train`, `mesokit-add-simulator`, `mesokit-add-model`,
`mesokit-add-trainer`, `mesokit-add-artifact`; see [Agent Skills](skills.md)). `list`
and `path` show what is installed and where; `install` copies skills into
the folder a coding agent scans so they can be invoked conversationally
outside the mesokit checkout.

```sh
mesokit skills list
mesokit skills path NAME
mesokit skills install [NAME ...] [--all] [--agent claude|codex] [--scope project|user] [--dest DIR] [--force]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `NAME …` | all shipped skills | Skills to copy (`--all` is the explicit form). |
| `--agent` | `claude` | Folder layout: `claude` (`.claude/skills/`, `~/.claude/skills/`) or `codex` (`.agents/skills/`, `$CODEX_HOME/skills`, default `~/.codex/skills`). |
| `--scope` | `project` | `project` writes under the current directory, `user` under your home. |
| `--dest DIR` | none | Explicit target folder; overrides `--agent` / `--scope`. |
| `--force` | off | Replace a skill folder that already exists (also how to refresh after upgrading mesokit). |

```sh
mesokit skills list
```

```text

mesokit-add-model     Write and register a custom dynamics model for mesokit from the user's own module — a new architecture, a physics-structured parameterisation, or a new potential / operator block for the shipped Onsager families — and verify it structurally before any training
```

## `mesokit agent`

Set up a coding agent (Claude Code, Codex CLI) for a project that uses
mesokit as an installed package. `mesokit skills install` gives the agent
the procedures; `agent init` gives it the project conventions — an
`AGENTS.md` saying where the registries and outputs live, that the
project's own code goes in `plugins/`, to start from smoke-sized settings,
and which skill does what — and installs the skills in the same step.

```sh
mesokit agent init [--dir PATH] [--agent claude|codex|both] [--no-skills] [--force]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--dir PATH` | `.` | Project root to write into. |
| `--agent` | `claude` | Whose project skill folder to fill: `claude` (`.claude/skills/`), `codex` (`.agents/skills/`) or `both`. `AGENTS.md` and `CLAUDE.md` are written regardless. |
| `--skills` / `--no-skills` | on | Also copy the shipped skills, as `mesokit skills install` would. |
| `--force` | off | Rewrite an existing mesokit section and replace installed skill folders (how to refresh after upgrading mesokit). |

What it writes:

- `AGENTS.md` — the mesokit section between `<!-- mesokit:begin -->` and
  `<!-- mesokit:end -->` markers. A new file holds only that section; an
  existing file gets it appended, and nothing outside the markers is ever
  changed. Codex reads this file directly.
- `CLAUDE.md` — a one-line `@AGENTS.md` import so Claude Code reads the
  same text; an existing `CLAUDE.md` only gains the import line if it is
  missing.
- `.claude/skills/<name>/` and / or `.agents/skills/<name>/` — the skills,
  skipping folders that already exist unless `--force`.

```sh
cd my-project
mesokit agent init
```

```text
created   /home/me/my-project/AGENTS.md
created   /home/me/my-project/CLAUDE.md
skills    6 installed, 0 kept -> /home/me/my-project/.claude/skills
start your agent in /home/me/my-project and describe the task; re-run with --force after upgrading mesokit
```

A second run without `--force` is refused rather than duplicating the
section:

```text
Invalid value: /home/me/my-project/AGENTS.md already has a mesokit section; pass --force to rewrite it
```

Inside the mesokit checkout the command is not needed: the repository's
own `AGENTS.md` covers both using and developing the toolkit.

## Recipes

**Smallest end-to-end run** (seconds on a CPU):

```sh
mesokit data generate --dyn allen_cahn_1d --config fdr --name ac_fdr
mesokit train --model spectral_onsagernet_1d --dyn allen_cahn_1d --data ac_fdr --epochs 1 --device cpu
mesokit interpret extract --model spectral_onsagernet_1d_v0 --artifact potential --output figs/potential.png
```

**The reference experiment:**

```sh
mesokit data generate --dyn allen_cahn_1d                       # allen_cahn_1d_v0, 1000 trajectories
mesokit train --model spectral_onsagernet_1d --dyn allen_cahn_1d --data allen_cahn_1d_v0
mesokit interpret extract --model spectral_onsagernet_1d_v0 --artifact all --output figs/son_v0/
```

**A parameter sweep with reproducible names** (one dataset and one
checkpoint per value, grouped under `checkpoints/allen_cahn_1d/eps-scan/`
with the table in its `runs.json`):

```sh
mesokit sweep --dyn allen_cahn_1d --model spectral_onsagernet_1d --param eps=0.05,0.1,0.2 --experiment eps-scan
mesokit model list --experiment eps-scan --sort train_loss
```

**A learning-rate scan on one dataset**, then the best run continued:

```sh
mesokit sweep --dyn allen_cahn_1d --model spectral_onsagernet_1d --data allen_cahn_1d_v0 \
  --train-param trainer.lr=1e-3,1e-4,1e-5 --experiment lr-scan --epochs 20
mesokit model list --experiment lr-scan --sort train_loss
mesokit model show lr-scan/spectral_onsagernet_1d_lr0.0001
mesokit train --from lr-scan/spectral_onsagernet_1d_lr0.0001 --name lr-scan/son_long --epochs 200
```

The same thing by hand, if you need a step in between:

```sh
for eps in 0.05 0.1 0.2; do
  mesokit data generate --dyn allen_cahn_1d --set eps=$eps --name ac_eps$eps
  mesokit train --model spectral_onsagernet_1d --dyn allen_cahn_1d --data ac_eps$eps --name son_eps$eps
done
```

**Your own solver's output:**

```sh
python my_export.py                                   # writes runs/my_data.h5 in the v1 layout
mesokit data register --name my_v0 --file runs/my_data.h5
mesokit train --model fno1d --dyn my_dynamics --data my_v0 --config default
```

The training recipe is looked up at `configs/train/my_dynamics/fno1d/default.yaml`,
so create that folder (copy one of the shipped recipes) before training on a
custom `dyn`.

**Data in some other format, converted by an agent:**

```sh
mesokit data parse --file ~/runs/field.nc --hint "variable phi, dims (member, time, x)" --name phi_v0
mesokit data list
```

**Two-dimensional pipeline**, including the physics check that the model
family reproduces the data-generating equation:

```sh
mesokit data generate --dyn allen_cahn_2d --config fdr --name ac2d_fdr        # 4 x 101 x 32 x 32, seconds
mesokit train --model spectral_onsagernet_2d --dyn allen_cahn_2d --data ac2d_fdr \
  --config physics_check_smoke --name ac2d_check                              # Km = 1, Kw = 0, analytic potential
mesokit train --model spectral_onsagernet_2d --dyn allen_cahn_2d --data ac2d_fdr --config smoke --name ac2d_son
mesokit train --model fno2d --dyn allen_cahn_2d --data ac2d_fdr --config smoke --name ac2d_fno
mesokit train --model onsagernet_2d --dyn allen_cahn_2d --data ac2d_fdr --config smoke --name ac2d_on
mesokit interpret extract --model ac2d_son --artifact potential --output figs/ac2d_son.png
```

**Classical OnsagerNet** (the grid as a `Nx`-dimensional ODE with learned
`M(x)`, `W(x)` and a coercive MLP potential) shares the `potential` artifact;
the `circulant` recipe makes `M` / `W` per-mode multipliers so the artifact
plots them:

```sh
mesokit train --model onsagernet_1d --dyn allen_cahn_1d --data allen_cahn_1d_v0 --name on1d_lowrank
mesokit train --model onsagernet_1d --dyn allen_cahn_1d --data allen_cahn_1d_v0 --config circulant --name on1d_circ
mesokit interpret extract --model on1d_circ --artifact potential --output figs/on1d_circ.png
```

The other 2D and microscopic datasets train the same way (`ising_2d` and
`cahn_hilliard_2d` ship `fno2d` / `spectral_onsagernet_2d` recipes):

```sh
mesokit data generate --dyn ising_2d --config kac --name ising_kac
mesokit train --model spectral_onsagernet_2d --dyn ising_2d --data ising_kac --epochs 20
mesokit data generate --dyn cahn_hilliard_2d       # ~10 min, ~210 MB
mesokit data generate --dyn llg_lattice_2d         # 3 channels; the shipped recipes train on all of them
mesokit train --model fno2d --data llg_lattice_2d_v0 --epochs 20
mesokit data generate --dyn peridynamics_fracture_2d --config fdr
```

**Index a checkpoint trained in a notebook and inspect it:**

```sh
mesokit model register --model nb_run --file checkpoints/nb/model.pt --config checkpoints/nb/config.yaml
mesokit interpret list --model nb_run
```

## Files the CLI Reads and Writes

| Path | Written by | Read by | Notes |
| --- | --- | --- | --- |
| `configs/data/<dyn>/*.yaml` | you | `data generate` | Hydra recipe; keys are simulator kwargs. |
| `configs/train/<dyn>/<model>/*.yaml` | you | `train` | Sections `model`, `dataset`, `dataloader`, `trainer`. |
| `data/<dyn>/<name>.h5` | `data generate` | `train`, `interpret` | v1 trajectory cache. |
| `data/parsed/<stem>.h5` | `data parse` (via the agent) | `train`, `interpret` | Same layout. |
| `.mesokit/datasets.json` | `data generate`, `data register`, `data parse` | `data list`, `train`, `interpret` | `name → {path, metadata}`; metadata holds shape, dtype, `dt`, the three groups. |
| `checkpoints/<dyn>/<run>/` | `train` | `interpret`, `model prune` / `sync` | `model.pt`, `config.yaml`, `history.json`, `run.json` (the run record), Lightning `.ckpt`. |
| `checkpoints/<dyn>/<experiment>/<run>/` | `train --experiment`, `sweep` | as above | The same files; registered as `<experiment>/<run>`. |
| `checkpoints/<dyn>/<experiment>/runs.json` | `train --experiment`, `sweep`, `model sync` | you (notebooks) | `{schema_version, experiment, dyn, model, created, updated, axes, data_axes, rows}`; one row per run (failed points included) with `run`, `checkpoint`, `dataset`, `params`, `data_params`, `metrics`, `status`, `data_status`, `wall_time_s`, `error`, the paths. |
| `.mesokit/checkpoints.json` | `train`, `sweep`, `model register` / `tag` / `remove` / `prune` / `sync` | `model list` / `show`, `interpret`, `train --from` | schema 2: `name → {path, config_path, run_dir, experiment, run, model_name, trainer_name, dyn, dataset_name, data, dataset_path, recipe, overrides, params, data_params, metrics, created, status, tags, notes, from, run_id, training_config_hash, metadata}`; schema-1 files (paths and names only) are read unchanged. |
| `checkpoints/<dyn>/sweeps/<timestamp>.json` | earlier versions of `sweep` (no longer written) | `model sync --import-sweeps` | `{dyn, model, params, created, rows}`; the legacy summary. |
| `AGENTS.md`, `CLAUDE.md` | `agent init` | your coding agent | Conventions for using mesokit in the project; the mesokit section sits between `<!-- mesokit:begin -->` / `<!-- mesokit:end -->` markers. |
| `.claude/skills/<name>/`, `.agents/skills/<name>/` | `skills install`, `agent init` | your coding agent | A copy of each shipped skill folder. |

Both registries are plain JSON with atomic writes; you can inspect or hand-edit
them (`mesokit model remove` / `prune` do the deleting for checkpoints).
Nothing under `data/`, `checkpoints/` or `.mesokit/` should be committed.

A registry entry, for reference:

```json
{
  "schema_version": 1,
  "entries": {
    "ac_fdr": {
      "path": "/home/me/mesokit/data/allen_cahn_1d/ac_fdr.h5",
      "metadata": {
        "dyn": "allen_cahn_1d",
        "shape": [10, 101, 1, 256],
        "data_dtype": "float32",
        "channel_names": ["u"],
        "dt": 0.001,
        "physical": {"Lx": 6.283185307179586, "T": 0.1, "eps": 0.1},
        "numerical": {"Nx": 256, "dx": 0.02454369260617026, "dt": 4e-05, "T_save_steps": 25, "Nk": 3, "max_k": 10, "dealias": 2},
        "provenance": {"seed": 0, "u_bound": 10.0}
      }
    }
  }
}
```

## Troubleshooting

| Message | Cause | Fix |
| --- | --- | --- |
| `config dir not found: …/configs/data/<dyn>` | Not running from the repository root, or `<dyn>` has no recipe folder. | `cd` to the root; check `mesokit data avail`; create `configs/data/<dyn>/default.yaml` for a custom simulator. |
| `no config 'x' under …; available: default, fdr` | `--config` takes a stem, not a filename or path. | Drop the `.yaml` and any directory. |
| `--name and --no-registry are mutually exclusive` | Both flags given. | Pick one. |
| `dataset 'x' already registered; pass --force to overwrite` | Name collision. | Choose another `--name`, or add `--force`. In a `sweep`, `--reuse-data` trains on the existing dataset instead. |
| `unknown parameter 'x' for simulator …; accepted: …` | A `--set` / `--param` key is not a keyword argument of the simulator. | Pick a key from the `accepted` list (they are the keys of the data recipe). |
| `allen_cahn_1d needs Dedalus, which is not installed` (or `… needs LAMMPS …`) | The simulator's solver back-end is a conda-forge package that `pip install mesokit` cannot bring in. | `pixi add dedalus` / `pixi add lammps` (or `conda install -c conda-forge …`) in the environment `mesokit` runs in; see [Installation](#installation). |
| `sanity check failed for …; not registered` (or `validation failed for …`) | The file violates the v1 contract; the specific checks are printed above the message. | Fix the writer — see [Data Structure](data_processing/structure.md) — and re-check with `mesokit data validate FILE`. |
| `output … already exists; pass --force to replace it` | `data parse` found a file at the output path before launching the agent. | Add `--force` to replace it, or pick another `--output`. |
| `unknown artifact 'x' for checkpoint 'y'; available: …` | `interpret extract` was given an artifact the model does not expose. | Pick one from the list (`mesokit interpret list --model y`). |
| `dataset 'x' is not registered and is not an existing HDF5 path` | `--data` matched neither a name nor a file. | `mesokit data list`, or pass the path. |
| `registered dataset 'x' points to missing file` | The file was moved or deleted after registration. | Re-register with the new path and `--force`, or regenerate. |
| `checkpoint 'x' is not registered` | `interpret` needs a name from `mesokit model list`. | Train, or `mesokit model register`; `mesokit model sync` re-indexes runs that are on disk but not in the registry. |
| `checkpoint 'x' is ambiguous; candidates: a/x, b/x` | Two experiments hold a run of that name. | Pass the full `<experiment>/<run>` key. |
| `--data cannot be combined with --param` / `--data is required when only --train-param axes are given` | A sweep with data axes generates its datasets; one without needs to be told what to train on. | Drop `--data`, or add it. |
| `--from: the weights of 'x' do not fit the model being trained` | `--set` or `--config` changed the architecture. | Keep the architecture keys as in the source checkpoint; `--set` only training keys. |
| `run directory … already holds a checkpoint` | `--name` (or the auto name) points at a directory with a `model.pt`, e.g. from a `--no-registry` run. | Pick another `--name`, add `--force` to overwrite it, or `mesokit model prune` the leftovers. |
| `--output must be a directory when --artifact all` | An extension was given with `--artifact all`. | Pass a directory path. |
| `agent 'claude' is not installed: no claude command on PATH` | The agent CLI is missing from the shell `mesokit` runs in; nothing was launched. | Follow the official installation guide the message names ([Claude Code](https://code.claude.com/docs/en/setup), [Codex CLI](https://developers.openai.com/codex/cli)), check `claude --version`, and re-run; or `--agent codex`. |
| `AGENTS.md already has a mesokit section; pass --force to rewrite it` | `agent init` was run in this project before. | Add `--force` to refresh the section; text outside the markers is kept. |
| A tensor size mismatch inside the model during `train` | The recipe's `model.Nx` does not match the dataset grid (e.g. the 8-point `smoke.yaml` fixture on 256-point data). | Use `--config default` or fix `Nx`. |
| Training is slow or out of memory | Default recipes assume a GPU. | `--device cpu --batch-size 8 --epochs 1` for a smoke run. |

## Python Equivalents

Everything the CLI does is available from Python; the CLI only adds the
registries and the config lookup.

| CLI | Python |
| --- | --- |
| `mesokit data avail` | `mesokit.data.available()` |
| `mesokit data generate --dyn X` | `ds = mesokit.data.simulate("X", **kwargs); ds.save_hdf5(path)` |
| `mesokit data validate F` / `register --file F` | `report = mesokit.data.validate(F)` (no registry write) |
| `mesokit train` | `TrajectoryDataset.load_hdf5(path)` → a `mesokit.data.datasets` adapter → `DataLoader` → `mesokit.trainers.get_trainer(name)(...).fit(model, loader)` |
| `mesokit sweep` | `mesokit.cli.sweep.run_sweep("X", "arch", {"eps": [0.05, 0.1]}, train_params={"trainer.lr": [1e-3, 1e-4]}, experiment="scan")` — the registries and naming included; returns the table rows |
| `mesokit model list` | read `.mesokit/checkpoints.json` (`--format json` prints the same records), each run's `run.json`, or an experiment's `runs.json` |
| `mesokit interpret list` / `extract` | `model.load_state_dict(torch.load("model.pt"))`; `model.list_artifacts()`; `model.artifact(name).save(path)` |

See [Training](training.md) and [Interpretability](interpretability.md) for
the full Python surface, and the custom pages of each section
([Custom Simulators](data_processing/custom_simulator.md),
[Custom Models](models/custom_model.md),
[Custom Trainers](training/custom_trainer.md),
[Custom Artifacts](interpretability/custom_artifact.md)) for registering your
own.
