# Command-Line Reference

Use `mesokit` to generate or import trajectory data, train models, manage
saved checkpoints, and extract figures describing what a model learned.
For a first run, follow the [Quickstart](quickstart.md). For combinations
of commands, see [CLI Workflows](cli/recipes.md).

(running-the-cli)=

## How to use the CLI

The examples in this guide assume `mesokit` is available in your shell.
In a Pixi or uv project, prefix each command with `pixi run` or `uv run`,
respectively:

```console
$ pixi run mesokit --help
$ uv run mesokit --help
```

Choose the command for your environment. With an activated environment
that has mesokit installed, use `mesokit --help` directly.

## Commands

| Command | Purpose |
| --- | --- |
| [`mesokit data`](cli/data.md) | List simulators; generate, validate, register, or convert datasets |
| [`mesokit train`](cli/train.md) | Train a model or continue from saved weights |
| [`mesokit sweep`](cli/sweep.md) | Run an experiment over a grid of simulation or training parameters |
| [`mesokit model`](cli/model.md) | List, inspect, tag, register, remove, or synchronize checkpoints |
| [`mesokit interpret`](cli/interpret.md) | List artifacts and save their figures |
| [`mesokit skills`](cli/skills.md) | List and install coding-agent skills |
| [`mesokit agent`](cli/agent.md) | Set up a coding agent for your project |

Every command accepts `--help`, for example `mesokit train --help`.
`mesokit --install-completion` installs shell completion;
`mesokit --show-completion` prints the completion script.

## Project directory and environment

Run commands from the **project directory** where you keep your work.
It can be any folder. Relative paths, local recipes, `plugins/`, and the
`.mesokit/` registries are resolved from this directory.

| Content | Default location |
| --- | --- |
| Generated datasets | `data/<dyn>/<name>.h5` |
| Training runs | `checkpoints/<dyn>/<run>/` |
| Runs grouped with `--experiment` | `checkpoints/<dyn>/<experiment>/<run>/` |
| Dataset and checkpoint indexes | `.mesokit/datasets.json`, `.mesokit/checkpoints.json` |
| Your data recipes | `configs/data/<dyn>/<stem>.yaml` |
| Your training recipes | `configs/train/<dyn>/<model>/<stem>.yaml` |

Recipes are YAML configuration files. Lookup checks the project's recipe
directory first, then the installed package, then the checkout for an
editable installation. `--config` also accepts a YAML path. See
[Training Recipes](training/recipes.md) for lookup details and overrides.

## Names and paths

A **model architecture** is a family such as `spectral_onsagernet_1d`.
A **checkpoint** is a saved training result, such as `son_demo`. The
meaning of `--model` depends on the command:

| Argument | Accepts |
| --- | --- |
| `train --model`, `sweep --model` | Architecture name |
| `train --data`, `sweep --data` | Registered dataset name or HDF5 path |
| `interpret --model`, `train --from` | Registered checkpoint name |
| `model register --model` | Name to assign to the checkpoint being registered |

Inside an experiment, checkpoint names are `<experiment>/<run>`. A bare
run name also works when it is unambiguous. Registries store paths to
files, not copies: moving or deleting a file can leave an entry pointing
to a missing file. See [checkpoint management](cli/model.md).

Without `--name`, datasets use the next available `<dyn>_v<n>` name and
training runs outside experiments use `<model>_v<n>`. Experiments use
names based on the changed parameters; see {ref}`Experiments <experiments>`.
Explicit name collisions are refused unless the command supports and is
given `--force`. File replacement rules differ by command and are listed
in each command's option table.

## Custom extensions

Each command imports Python modules and packages in `./plugins/` before
running. Names beginning with `_` or `.` are skipped. An import failure
stops the command and identifies the module and error. This lets your
simulators, models, and trainers register names used by the CLI, and lets
recipes refer to their classes through `_target_`.

Start with [Custom Simulators](data_processing/custom_simulator.md),
[Custom Models](models/custom_model.md), [Custom Trainers](training/custom_trainer.md),
or [Custom Artifacts](interpretability/custom_artifact.md).

## Output and errors

Data generation normally hides solver logs and shows progress on stderr
only in a terminal. Use `--verbose` / `-v` for solver logs, additional
metadata, and progress lines that remain readable in redirected output.
Training uses Lightning's progress bar, controlled by the recipe key
`trainer.enable_progress_bar`.

Argument, lookup, and validation errors normally exit with status `2`.
Unexpected failures produce a traceback and status `1`. A simulator error
is summarized by default; `data generate -v` includes its traceback.
Missing solver dependencies always produce an installation hint. Sweeps
continue past individual failed runs and exit with status `1` if any
point failed. See [Troubleshooting](cli/troubleshooting.md) for common fixes.
