# Training Recipes

`mesokit train` is driven by Hydra YAML recipes, but you rarely have to
write one: the shipped recipes come with the package, any key can be
changed for a run with `--set`, the model's grid is read from the dataset,
and a dataset / model pair with no recipe trains with built-in defaults.
Recipes for the shipped datasets and families are listed on each
[model page](../models.md); this page is where they are found, their
format, and when to write your own.

## Where Recipes Are Found

`configs/<kind>/<parts>/<stem>.yaml` is looked up in order:

1. `./configs/` in the working directory — your project's own recipes,
   which shadow the shipped ones of the same name;
2. `mesokit/configs/` inside the installed package — the shipped recipes
   (this is what a `pip install` user gets);
3. `configs/` at the repository root — the same files in an editable
   install from a checkout.

`--config` may also be a path to any YAML file, which bypasses the lookup.
`mesokit data generate` uses the same rule for `configs/data/<dyn>/`.

## Recipes Are Optional

With no recipe directory for a dataset / model pair, `mesokit train`
synthesises one: the model's constructor defaults plus the dataset's grid,
`SnapshotPairDataset` with `stride: 1`, dataloader defaults, and the
registered trainer's defaults. `--set key.path=value` (repeatable, values
parsed as YAML) changes any key on top of a recipe or of those defaults:

```sh
mesokit train --model spectral_onsagernet_1d --data my_data --set trainer.lr=1e-4 --set model.potential.eps=0.05
```

The completed configuration is written to
`checkpoints/<dyn>/<run>/config.yaml`; it is itself a valid recipe, so
`--config checkpoints/<dyn>/<run>/config.yaml` reproduces a run, and
copying it into `configs/train/<dyn>/<model>/<stem>.yaml` turns it into a
named variant. Write a recipe by hand when a configuration is worth naming
and sharing; otherwise `--set` is enough.

## Layout

```text
configs/train/<dyn>/<model>/<stem>.yaml
```

`<dyn>` is the dataset's dynamics name, `<model>` the registered
architecture name, and `<stem>` the recipe selected by `--config <stem>`
(default `default`). Sibling files are variants; `smoke.yaml` recipes are
tiny CPU fixtures (few epochs, small networks). No shipped recipe writes a
grid key, so each runs on any grid of its dynamics.

The data side has the same convention: `configs/data/<dyn>/default.yaml`
is the recipe `mesokit data generate --dyn <dyn>` uses, and its `_target_`
may be any importable callable that satisfies the simulator contract
([Custom Simulators](../data_processing/custom_simulator.md)).

## The Four Sections

```yaml
model:                    # constructor kwargs of the registered class
  _target_: mesokit.models.spectral_onsagernet.spectral_onsagernet_1d.SpectralOnsagerNet1d   # optional; defaults to the registered class
  # Nx, Lx: not written; read from the dataset (see below)
  potential: null         # nested components are Hydra objects too

dataset:                  # the training view wrapping the TrajectoryDataset
  _target_: mesokit.data.datasets.snapshot_pair_dataset.SnapshotPairDataset
  stride: 1
  # channel: 0            # pick one field of a multi-channel dataset

dataloader:               # torch.utils.data.DataLoader kwargs
  batch_size: 32
  shuffle: true
  num_workers: 0

trainer:                  # LitTrainer kwargs (or the registered trainer's)
  max_epochs: 100
  lr: 1.0e-3
  dt: null                # null: infer from the data
  accelerator: auto
  rollout_steps: 1
```

- **`model`** — keyword arguments of the model constructor. `_target_`
  defaults to the class registered under `--model` (shipped, or your own
  from `plugins/`) and is required only for an unregistered name (see
  [Custom Models](../models/custom_model.md)). Nested components (a
  potential, an operator block) are Hydra objects with their own `_target_`.
- **`dataset`** — the `TrajectoryDataset` wrapper; `mesokit train` calls it
  with `traj=<the loaded dataset>` plus these keys. See
  [Training Views](training_views.md).
- **`dataloader`** — merged over `{batch_size: 32, shuffle: true,
  num_workers: 0}`; `--batch-size` overrides `batch_size`.
- **`trainer`** — hyperparameters of the trainer registered for the model
  (`--trainer` overrides the name; a model with no trainer of its own gets
  `LitTrainer`; any class can be named by `trainer._target_`); `dt: null`
  means "infer from the data". `--epochs`
  overrides `max_epochs`, `--device` overrides `accelerator`. The full
  option list is on [LitTrainer](lit_trainer.md).

## The Grid Comes From the Dataset

Grid keywords a constructor accepts but the recipe leaves out are filled
from the dataset, recursively for nested components: `Nx` / `Ny` / `Nz`
from `grid_shape`; `Lx` / `Ly` / `Lz` from the `physical` group (`2π` when
`Lx` is absent, a missing later axis repeating the first); `grid_shape`
and `domain` of a nested potential; `in_dim` (the number of grid points)
and `grid_shape` of the classical OnsagerNet's blocks. A written box length
is kept (a dataset may lack `Lx`); a written number of grid points (`Nx`,
`grid_shape`, `in_dim`) that contradicts the dataset is refused before
training starts, naming the key. The shipped recipes carry no grid keys at
all — leave them out of recipes you write too, and they run on any grid of
their dynamics. Two things are not inferred: multi-channel
datasets need `dataset.channel` (the shipped models are single-channel),
and a potential's `eps` or a block's rank are modelling choices, not
grid facts.

## A Recipe for Your Own Dynamics

A built-in model on your own dynamics needs no recipe: the defaults plus
the dataset's grid apply, and `--set` adjusts them. To keep a
configuration, copy the closest shipped recipe for the same family and
dimension, for example
`configs/train/allen_cahn_1d/spectral_onsagernet_1d/default.yaml` to
`configs/train/decay_1d/spectral_onsagernet_1d/default.yaml` (nothing in
it depends on the grid), then:

```sh
mesokit train --model spectral_onsagernet_1d --data decay_1d_v0 --epochs 5 --device cpu
```

The saved `checkpoints/<dyn>/<run>/config.yaml` is the resolved recipe
with `model_name`, `dyn`, `dataset_name` and `checkpoint_name` added; it
is what `mesokit interpret` uses to rebuild the model.
