# Data Structure

Three distinct objects in `mesokit` all get called "data" or "dataset"
in conversation. Naming them up front prevents the rest of this page
from being ambiguous:

| Object | Concrete type | Lifetime | Role |
| --- | --- | --- | --- |
| Cache file | HDF5 file (`*.h5`) | Persistent on disk | The interchange format; what `mesokit data generate` writes and `mesokit data register` accepts. |
| In-memory bundle | `TrajectoryDataset` (Python `@dataclass`) | One per file load | The canonical Python container; what every model and interpretability extractor consumes. |
| Training view | Subclasses of `torch.utils.data.Dataset` | One per training run | Samplers that slice an in-memory bundle into batched `(input, target)` pairs for a `DataLoader`. |

**`TrajectoryDataset` is not a `torch.utils.data.Dataset`.** The shared
word "Dataset" is unfortunate but historical: `TrajectoryDataset` is a
plain dataclass holding tensors and dicts, while the training views are
PyTorch samplers whose `__getitem__` slices over that bundle. Likewise,
the word "dataset" inside an HDF5 file is the h5py term for a named
array — a third unrelated usage.

This page is the canonical reference for the cache file and the
in-memory bundle (its Python mirror). The training views are summarized
at the bottom with a pointer to their module reference.

The detailed v1 schema is defined in code by
{py:data}`mesokit.data.format.TRAJECTORY_CACHE_V1` (also re-exported as
{py:data}`mesokit.data.format.CURRENT_TRAJECTORY_CACHE_FORMAT`). The
tables below are rendered from that schema; the prose explains the
conventions around it.

## Cache File (HDF5)

The cache file is the source of truth for interchange. The Python helper
[`TrajectoryDataset.save_hdf5`](../../src/mesokit/data/trajectory.py)
produces this layout, and the matching `load_hdf5` parses it back; an
external exporter (numpy / MATLAB / a custom solver) can produce the
same layout directly with `h5py` (see [Custom Datasets](custom.md)).

```text
<dataset>.h5
├── (root attrs)
│   ├── format        "mesokit-trajectory"
│   ├── version       1
│   ├── dyn           <string>
│   ├── data_dtype    "float32" | "float64" | ...
│   └── channel_names (optional) array<string>
├── data         h5py dataset, shape (n_traj, n_time, n_channel, *grid_shape)
├── times        h5py dataset, shape (n_time,)
├── physical/    group with arbitrary scalar attrs
├── numerical/   group with arbitrary scalar attrs
└── provenance/  group with arbitrary scalar attrs
```

Two required h5py datasets live at the root; metadata is partitioned
across the closed root attributes and the three open-content groups.

### Required H5py Datasets

In HDF5 terminology, a "dataset" is a named array stored inside a file.
These are the two arrays the schema requires, with the shape and dtype
checks the validator applies to each.

```{trajectory-cache-format} datasets
```

### Root Attributes

Root attributes are a **closed** set: the validator rejects any
root-level attribute not listed below. Domain-specific or equation-
specific values belong inside one of the three metadata groups, never at
the root.

```{trajectory-cache-format} attributes
```

### Metadata Groups

Metadata is partitioned by meaning into three HDF5 groups. Each group's
`.attrs` is **open**: writers may include any HDF5-attribute-compatible
scalar, string, or simple array. The example-key columns below document
conventions, not a closed set.

```{trajectory-cache-format} groups
```

The split matters because the three categories age differently:

- `physical/` describes the continuum problem — these values are
  properties of the equation and domain (`Lx`, `T`, `eps`) and travel
  with the dataset forever.
- `numerical/` describes the discretization — `Nx`, `dx`, `dt`,
  integrator knobs (`T_save_steps`, `dealias`, …). Resampling,
  downscaling, or rerunning with a different scheme produces a new file
  with a new `numerical/` block but typically the same `physical/`.
- `provenance/` is about how this particular file was produced — seeds,
  rejection thresholds, generator references, source identifiers. Two
  files with identical `physical/` and `numerical/` can still differ
  here.

### Axis Contract

`data[i, j, c, ...]` is channel `c` of trajectory `i` at time `times[j]`.

All trajectories in the same file share the same `times` and
`channel_names`. Single-field equations use `n_channel = 1` and
`channel_names = ("u",)`; multi-field systems list one name per coupled
component.

The `n_channel` axis is always present — even when there is only one
field. This keeps the contract uniform across single- and multi-channel
data; training-view adapters that target single-field models can select
a channel up-front (see below).

### Dtype Rules

- `data` must have a floating dtype, and its actual dtype must match the
  string declared in the `data_dtype` root attribute (commonly
  `"float32"` or `"float64"`). Mismatches are a validator error: writers
  must keep the attribute in sync with the array.
- `times` must have a floating dtype. Its precision is not declared
  separately; pick `float64` if step sizes need it.
- Group attributes are passed through `h5py` and round-tripped via the
  shared decoder in [`_hdf5.py`](../../src/mesokit/data/_hdf5.py) so
  `bytes`/`str`, 0-d NumPy arrays, and list-shaped values come back as
  native Python types.
- Finite values are required for `data` and `times`; `NaN` / `Inf` are
  rejected by the validator.

## In-Memory Bundle (`TrajectoryDataset`)

[`TrajectoryDataset`](../../src/mesokit/data/trajectory.py) is a Python
`@dataclass` (not a `torch.utils.data.Dataset`). It mirrors the cache
file one-to-one: every required HDF5 entry has a corresponding dataclass
field, and the three open-content metadata groups become three plain
Python dicts.

| Field | Type | Mirrors (on disk) | Notes |
| --- | --- | --- | --- |
| `data` | `Tensor` | `data` dataset | Shape `(n_traj, n_time, n_channel, *grid_shape)`. |
| `times` | `Tensor` | `times` dataset | Shape `(n_time,)`. Floating, strictly increasing. |
| `dyn` | `str` | `dyn` root attr | Compulsory dynamics identifier (e.g. `"allen_cahn_1d"`). |
| `physical` | `dict[str, Any]` | `physical/.attrs` | Equation/domain parameters. Open-content. |
| `numerical` | `dict[str, Any]` | `numerical/.attrs` | Discretization and solver parameters. Open-content. |
| `provenance` | `dict[str, Any]` | `provenance/.attrs` | How this file was produced. Open-content. |
| `channel_names` | `tuple[str, ...] \| None` | `channel_names` root attr | Optional channel labels; length must equal `data.shape[2]`. |

Convenience properties:

- `n_traj`, `n_time`, `n_channel` — integer accessors for the three
  leading axes of `data`.
- `grid_shape` — tuple of the remaining trailing axes (e.g. `(Nx,)` for
  1D).
- `metadata` — read-only flat view bundling `dyn`, `channel_names`, and
  the three group dicts for one-shot inspection.

The dataclass enforces the cache-file invariants at construction time
(non-empty `dyn`, `data.ndim >= 4`, `times.shape == (n_time,)`,
`len(channel_names) == n_channel`), so an in-memory bundle that
type-checks is guaranteed to round-trip through `save_hdf5` /
`load_hdf5` without losing information.

## Training Views (`torch.utils.data.Dataset` adapters)

A `TrajectoryDataset` is not directly iterable by a
`torch.utils.data.DataLoader`. The package ships two thin adapters in
{py:mod}`mesokit.data.datasets` that wrap a `TrajectoryDataset` and
expose the standard `__len__` / `__getitem__` interface expected by
PyTorch:

| Adapter | Yields | Use case |
| --- | --- | --- |
| `SnapshotPairDataset` | `(u_t, u_{t+stride})` | Autoregressive one-step (or `k`-step) predictors. |
| `LookbackWindowDataset` | `(stack(u_{t-k+1}, ..., u_t), u_{t+lead})` | Models that condition on more than the current state (RNN-style, memory). |

Both adapters take a `channel: int = 0` kwarg so they yield
`(*grid_shape,)`-shaped samples by default — preserving the
single-channel input contract that built-in models like `FNO1d` and
`SpectralOnsagerNet1d` expect. Multi-channel datasets either select one
channel per adapter instance, or a future model can consume the full
`data[i, t, :, :]` tensor directly.

These adapters are toolkit examples, not requirements — every trainer
in `mesokit.trainers` accepts an arbitrary `torch.utils.data.DataLoader`,
so a user is free to write their own adapter if their paper needs a
different sampling view (operator pairs, contrastive crops, …). See
[Examples](examples.md) for end-to-end usage.
