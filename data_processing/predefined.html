Predefined Datasets¶

mesokit ships a catalog of pre-defined simulators that produce conforming trajectory cache files out of the box. They are the fastest way to obtain a dataset that downstream models, trainers, and interpretability extractors can immediately consume — no schema bookkeeping required — and they span the three kinds of data the toolkit is built for: phase-field PDEs (Allen–Cahn, Cahn–Hilliard), dispersive waves (KdV), and microscopic / particle-level dynamics coarse-grained to a field (Ising Monte Carlo, Landau–Lifshitz–Gilbert spin lattices, peridynamic fracture).

The catalog is registered automatically when mesokit.data is imported, and the same simulator can be called from the CLI, from a notebook, or from a training script through the universal simulate(name, **params) surface.

LAMMPS + SciPy

Dedalus and LAMMPS are conda-forge packages: the checkout’s sim Pixi feature has both, a pip install mesokit has neither. The simulators that need them import the back-end only when run, so mesokit.data, the CLI and the three NumPy/SciPy simulators work without it; running one of the four without its back-end stops with the exact command to run:

Invalid value: allen_cahn_1d needs Dedalus, which is not installed (No module named 'dedalus'). It is a conda-forge package, not a PyPI one: run `pixi add dedalus` in a pixi project or `conda install -c conda-forge dedalus` in a conda environment, then re-run.

The same message names lammps for peridynamics_fracture_2d. See Solver Back-Ends.

Listing What’s Available¶

From the CLI:

mesokit data avail

prints the registered simulators along with the Python target each one dispatches to. Programmatically:

from mesokit.data import available, get

print(available())           # ['allen_cahn_1d', 'allen_cahn_2d', 'cahn_hilliard_2d', 'ising_2d', 'kdv_1d', ...]
sim = get("allen_cahn_1d")   # the simulator callable

mesokit data list is the complementary command for already-registered datasets on disk; see Custom Datasets for the registration workflow.

Generating From the CLI¶

The most common entry point is the data generate subcommand:

mesokit data generate --dyn allen_cahn_1d --config default

This runs the registered simulator with the parameters from configs/data/allen_cahn_1d/default.yaml, writes the resulting HDF5 file under data/allen_cahn_1d/<auto-name>.h5, and registers the file under that auto-generated name (<dyn>_v<n> — the next free v0, v1, …).

Every simulator ships a default.yaml (the reference dataset) and an fdr.yaml (“fast dev run”: a few trajectories, seconds of compute) under configs/data/<dyn>/; some ship further variants (for example configs/data/ising_2d/kac.yaml). Select one by stem:

mesokit data generate --dyn ising_2d --config kac

Useful flags:

  • --name my_run — explicit registry name instead of the auto <dyn>_v<n>. A name that is already registered is refused before the solver starts, unless --force, so a long run is never spent on a dataset that cannot be recorded.

  • --output path/to/file.h5 — explicit output path instead of the default. A file already there is replaced, with a warning on stderr before the solver starts.

  • --no-registry — write the file but skip the registry (the --name flag is rejected in this mode). Nothing is validated either, and the printed block says so.

  • --verbose / -v — keep the underlying solver’s per-step logs visible, report progress as plain lines that survive a pipe, and print the full metadata at the end. Default is quiet: no solver log, and a single overwriting progress line on stderr only when stderr is a terminal, so a redirected or captured run stays silent.

Each run prints what it wrote and what the validator made of it. For mesokit data generate --dyn allen_cahn_1d --config fdr in a fresh project:

wrote data/allen_cahn_1d/allen_cahn_1d_v0.h5 (1019.3 KiB)
  check:      passed (mesokit-trajectory v1)
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u
  registry:   allen_cahn_1d_v0

The simulator’s metadata (the physical / numerical / provenance groups described in Data Structure) is filled in from the config and from generator-side facts like the random seed; -v prints it.

Generating Programmatically¶

The same simulators are accessible by name from Python:

from mesokit.data import simulate

ds = simulate("allen_cahn_1d", eps=0.1, Nx=256, T=0.1)
ds.save_hdf5("data/ac_quick.h5")     # optional — same v1 layout as the CLI

simulate(name, **params) dispatches to the registered callable with the kwargs you provide; defaults match the canonical config in configs/data/<name>/default.yaml. The returned TrajectoryDataset is ready to feed into a SnapshotPairDataset or LookbackWindowDataset without saving to disk first.

What Ends Up in the File¶

Built-in simulators populate metadata according to a consistent scheme. For allen_cahn_1d (defaults shown):

root attrs
  format         "mesokit-trajectory"
  version        1
  dyn            "allen_cahn_1d"
  data_dtype     "float32"
  channel_names  ["u"]

physical/
  Lx    6.283185307179586
  T     0.1
  eps   0.1

numerical/
  Nx             256
  dx             0.02454369260617026
  dt             4e-05
  T_save_steps   25
  Nk             3
  max_k          10
  dealias        2

provenance/
  seed     0
  u_bound  10.0

Every value is either a keyword argument of the simulator or derived from one (dx = Lx / Nx, T = n_steps · dt, particle counts, scheme labels) — the per-simulator sections below list them — and the on-disk file has the same v1 layout as one produced by the minimal external-writer snippet in Custom Datasets.

Simulator Catalog¶

Jump to a system:

  • Allen–Cahn, 1D

  • Allen–Cahn, 2D

  • Korteweg–de Vries

  • Cahn–Hilliard

  • Ising

  • Landau–Lifshitz–Gilbert

  • Peridynamic fracture

Each entry gives the model, what the trajectories represent, the complete numerical scheme (discretisation, time stepping, de-aliasing, stability limits, what is conserved exactly and what is not), the initial-condition distribution, the parameters exposed through configs/data/<dyn>/*.yaml (which are exactly the keyword arguments of the Python simulator), and references. The scheme descriptions are written so that the file could be regenerated from them without reading the source. Throughout, T in a config is the final simulated time for PDE solvers and the temperature for the stochastic Ising sampler; the tables say which.

Test that a learned model does not invent dissipation

cahn_hilliard_2d.

Start from a genuinely microscopic, stochastic system and check the learned mesoscopic law against a known limit

ising_2d --config kac.

Learn a reversible + dissipative (Onsager) structure from multi-channel data

llg_lattice_2d.

Learn a damage / phase-field fracture model from particle mechanics

peridynamics_fracture_2d (needs the sim feature for LAMMPS).

The shipped model families are registered per dimension (fno1d/2d/3d, spectral_onsagernet_1d/2d/3d, onsagernet_1d/2d/3d, see Models); what they see of a multi-channel dataset — one field, every channel or a list of them — is the channel selection of the stock adapters, and Custom Models covers registering a model of your own.
