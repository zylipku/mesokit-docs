Architecture¶

This document describes how mesokit (this repo’s package) is structured and where it is going. Read README.md first for what the project is and how to run it; this document is for contributors who want to understand or extend the codebase.

Overall principles¶

mesokit contains a complete pipeline from data loading, through network training, to interpretability extraction. In the future, we aim to release it as a PyPI / conda package.

  • Modular components, single data shape. Data simulators and model families live in independent sub-packages, each with its own protocol; model-family interpretability artifacts live beside the model internals that construct them. They compose through one canonical in-memory object — TrajectoryDataset (see Data below) — so a new component can be added without touching the others.

Data¶

All training data is many temporal trajectories. The canonical in-memory object is TrajectoryDataset with shape (n_traj, n_time, *spatial) plus a mesh, times, and free-form metadata dict. Every model and every interpretability extractor consumes this object.

Physical / equation parameters (eps for Allen-Cahn, etc.) travel as metadata, so a parameter sweep is just multiple datasets sharing the same shape — no schema crystallizes until external datasets need to be ingested.

Operator methods (FNO, DeepONet) whose natural training data is (input function, query) → value own a small adapter that constructs their pairs from a TrajectoryDataset at load time. The adapter lives next to the operator module so the rest of the toolkit doesn’t have to know about it.

Producer protocol¶

A simulator is any callable that takes keyword parameters and returns a TrajectoryDataset:

@runtime_checkable
class Simulator(Protocol):
    def __call__(self, *, verbose: bool = False, **params: object) -> TrajectoryDataset: ...

The keyword-only signature keeps name-dispatched calls (simulate("allen_cahn_1d", eps=0.1, ...)) and direct calls interchangeable. Concrete simulators register themselves through mesokit.data.register and are looked up by name. Identifying parameters (dyn, eps, Lx, T) should be echoed into the returned dataset’s metadata so a downstream consumer can recover them without out-of-band bookkeeping.

Standard kwargs. Every simulator must accept verbose: bool = False. With verbose=False the simulator should suppress per-step solver chatter and emit a single concise progress signal (e.g. accepted/total trajectories on stderr); with verbose=True it should leave the underlying solver’s logs alone. The CLI mesokit data generate forwards its --verbose flag through this kwarg, so a simulator that omits it will raise TypeError at instantiation time. This is the only standard kwarg today — extend the list only when another cross-cutting concern appears.

Per-dyn config tree¶

Hydra configs for mesokit data generate live under configs/data/<dyn>/, one folder per registered dynamics:

configs/data/
├── allen_cahn_1d/
│   ├── default.yaml     # used when --config is omitted
│   └── <variant>.yaml   # selected via --config <variant>
└── kdv_1d/
    └── default.yaml

default.yaml is the canonical recipe — it should reproduce the parameters the simulator’s docstring promises, so mesokit data generate --dyn <dyn> with no further flags is the lowest-friction path to the reference dataset. Sibling YAMLs are variants (e.g. eps05.yaml, fdr.yaml, parameter sweeps); they are selected by stem with --config <stem> and resolve to configs/data/<dyn>/<stem>.yaml. The CLI never accepts a free path here — keeping configs inside the per-dyn folder makes them discoverable (the error message on a typo lists what is available) and keeps reproducible recipes checked in alongside the simulator they parameterize.

This protocol is intentionally narrow: it admits PDE solvers, particle and agent-based simulations producing coarse-grained trajectories, and offline data loaders that read from disk on equal footing — anything is a Simulator if its __call__ has the right shape.

On-disk format¶

TrajectoryDataset round-trips to HDF5 via save_hdf5 / load_hdf5. The detailed cache-file contract is the mesokit.data.format.TRAJECTORY_CACHE_V1 schema, with the human overview in Data Format. The v1 layout is deliberately flat and matches what the code reads today:

my_data.h5
├── data    [dataset]   shape (n_traj, n_time, *spatial),  numeric dtype
├── times   [dataset]   shape (n_time,),                   numeric dtype
├── mesh    [dataset]   shape (*spatial,),                 numeric dtype
└── attrs/                                                 free-form metadata
    ├── dyn            e.g. "allen_cahn_1d", "kdv_1d"
    ├── eps            e.g. 0.1
    └── ...            any HDF5-compatible scalar / string

The three top-level datasets are required; everything else lives on the file’s attributes and round-trips into the in-memory metadata dict. The format is deliberately flat so a user can build it by hand from any source — PDE solvers, finite-difference codes, MD, agent-based simulations — without learning a domain-specific schema. The same file is what built-in simulators emit when called from mesokit data generate, so generated and user-supplied datasets are indistinguishable to the rest of the toolkit.

The current format is a single trajectory bundle only. Paired microscopic/mesoscopic data should be introduced as a versioned extension with explicit groups rather than hidden inside free-form metadata.

Custom datasets¶

Users bring their own HDF5 file following the cache contract and register it under a name:

mesokit data register --name my_dataset --file data/my_data.h5

The registry entry maps my_dynamics to the file path; subsequent mesokit data ... and training runs resolve --dyn my_dynamics through the same dispatch as built-in simulators, with the loader returning the on-disk dataset directly.

Before the entry is written, a sanity check validates the file. It verifies:

  • the file opens as HDF5 and contains the three required datasets data, times, mesh;

  • data has at least three axes; the inferred shape is (n_traj, n_time, *spatial);

  • times is one-dimensional with shape (n_time,), monotonically increasing, and finite;

  • mesh has shape (*spatial,) matching the trailing dimensions of data;

  • all three datasets have numeric dtypes and contain no NaN / Inf values.

On success the CLI prints the inferred summary — n_traj, n_time, spatial_shape, dt (when the time grid is uniform, with a tolerance), and the metadata attributes read off attrs/ — so the user can confirm the file was interpreted as intended. On failure the message points at the specific axis, dataset, or attribute that did not match, and the file is not registered.

The sanity check is also exposed as a standalone helper (mesokit.data.validate(path) -> ValidationReport) so a user can run it without committing to registration — for example, inside a notebook while still preparing their export pipeline.

Model¶

A model in mesokit.models is a learnable dynamical system that advances state in time and exposes one or more named interpretability artifacts. The structural surface is four methods:

@runtime_checkable
class DynamicsModel(Protocol):
    def forward(self, u: Tensor, dt: float) -> Tensor: ...
    def rollout(self, u0: Tensor, n_steps: int, dt: float) -> Tensor: ...

    def list_artifacts(self) -> list[str]: ...
    def artifact(self, name: str) -> InterpretabilityArtifact: ...

forward advances one step; rollout iterates from an initial state; both operate on tensors with a leading batch dimension.

A single model can carry several artifacts that look at it from different angles — a learned free-energy landscape and a per-mode mobility diagnostic both come naturally out of a Spectral OnsagerNet, for example. The pair list_artifacts() / artifact(name) handles this:

  • list_artifacts() returns the names of the artifacts this model can produce. The list is per-model and per-trained-instance; there is no toolkit-wide enumeration.

  • artifact(name) builds the named artifact on demand. The call is expected to be lazy, since some artifacts require nontrivial post-processing (a grid sweep over a learned potential, a perturbation study, a sparsity report). Unknown names raise KeyError.

Each name resolves to a family-specific subclass of InterpretabilityArtifact implemented in the producing model package — a PotentialLandscape from a Spectral OnsagerNet, an OperatorDiagnostics from an FNO, a SymbolicLaw from a SINDy model — see Interpretability for the artifact contract. The CLI is a thin wrapper over this pair:

  • mesokit interpret list --model MODEL_NAME calls list_artifacts().

  • mesokit interpret extract --model MODEL_NAME --artifact NAME calls artifact(NAME) and renders the result.

Producing at least one artifact is part of the contract, not an opt-in: the comparison harness relies on every registered model returning a non-empty list so it can lay results from different families side by side.

The protocol is structural (typing.Protocol), not an ABC: any class exposing these three methods qualifies, with no inheritance required. Two implementation patterns cover the existing families:

  • rhs + stepper. The model implements rhs(u) for the right-hand side du/dt; forward and rollout are composed from rhs and a shared explicit stepper (Euler / RK4) provided as free helpers in mesokit.models. SINDy follows this pattern with a sparse symbolic rhs; FNO1d follows it with an FNO net as rhs.

  • Custom forward. Models that need a learned operator mapping between time slices, or a time-stepping scheme that does not factor through rhs (implicit, spectral, Fourier-space SBDF, etc.), implement forward directly. For example, SpectralOnsagerNet1d implements forward as SBDF1 in Fourier space — in that implementation, L and N refer to the linear and nonlinear parts of ∂V/∂u inside the potential, not to anything else.

Model registry¶

Every model family lives in its own sub-package under src/mesokit/models/ (e.g. fno/, spectral_onsagernet/) and registers itself with a central registry:

from mesokit.models import register, DynamicsModel

@register("spectral_onsagernet_1d")
class SpectralOnsagerNet1d(DynamicsModel):
    ...

The registry lets training, the CLI, and the comparison harness construct a model by name without importing it directly. New families add themselves by creating a module and registering one or more entries — no edits to a central switch statement.

Importing mesokit.models transitively imports each concrete model module as a side effect, so the registry is populated at package-import time. The “model zoo” is this registry of architectures. There is no plan to ship pretrained checkpoints; that would be a separate decision with hosting and versioning costs.

Training¶

Training is a separate layer from mesokit.models: model modules define architectures and interpretability hooks, while mesokit.trainers defines how a family is fit. The shared surface is intentionally small:

@runtime_checkable
class Trainer(Protocol):
    def fit(
        self,
        model: nn.Module,
        train_loader: DataLoader,
        val_loader: DataLoader | None = None,
    ) -> TrainResult: ...

Concrete trainers live under src/mesokit/trainers/<kind>/ and register by model name. mesokit train --model spectral_onsagernet_1d therefore resolves LitTrainer by default, while --trainer NAME can select an alternative. Heavy training dependencies belong behind the concrete trainer: mesokit.trainers imports cheaply, and the generic Lightning trainer imports Lightning only when fit() runs.

The trainer accepts a standard torch.utils.data.DataLoader; the package ships small adapters in mesokit.data.datasets for common views over TrajectoryDataset:

  • SnapshotPairDataset(traj, stride=1) yields (u_t, u_{t+stride}).

  • LookbackWindowDataset(traj, lookback, lead=1, stride=1) yields a history window and a future target.

The CLI owns registry side effects. Trainer.fit writes training artifacts and returns a TrainResult; mesokit train writes the resolved config.yaml, keeps history.json beside the checkpoint, and registers into .mesokit/checkpoints.json unless --no-registry is passed. The canonical artifact is always model.pt, a plain state_dict that can be loaded through the model registry without Lightning.

Interpretability¶

An interpretability artifact is what a model returns from artifact(name): a structured, self-describing object summarising what the model learned in a form a researcher can read, plot, or save. The shared surface is small — three labels, a one-paragraph summary, a plot, and a save helper:

@runtime_checkable
class InterpretabilityArtifact(Protocol):
    model_name: str
    dyn_name: str
    artifact_name: str

    def summary(self) -> str: ...
    def plot(self, ax: Any | None = None) -> Any: ...
    def save(self, path: str | Path, **kwargs: Any) -> Path: ...

The three name attributes label the artifact in side-by-side reports; artifact_name matches the entry from the producing model’s list_artifacts(), so an extracted artifact can be traced back to the call that produced it. summary() returns one paragraph of plain text; plot(ax=None) renders to a matplotlib axis, or returns a figure when no axis is given; save(path) lets the artifact class own its complete visualization. The protocol is structural (typing.Protocol), not an ABC: any object exposing those attributes and methods qualifies, with no inheritance required. Notebook display (_repr_html_) is not part of the contract — a free helper that falls back to summary() is available for subclasses that want it.

Beyond the protocol, each family carries whatever fields are natural for its own analysis:

Family

Subclass (planned)

Carries

OnsagerNet

PotentialLandscape

V on a grid, Km / Kw per-mode multipliers, slices

SINDy

SymbolicLaw

sympy expression, sparsity stats, LaTeX render

Operator (FNO, DeepONet)

OperatorDiagnostics

per-mode error spectrum, response to perturbations

Construction lives on the model and the concrete artifact class lives in the same model-family package. model.artifact("potential") returns a PotentialLandscape populated from the model’s own internals; model.artifact("spectrum") returns an OperatorDiagnostics. The model knows what it learned and is responsible for packaging that knowledge — no external extractor reaches into private attributes to assemble it.
