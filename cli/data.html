mesokit data¶

Produce or catalog trajectory datasets. The on-disk contract every subcommand reads or writes is the v1 HDF5 cache described in Data Processing. generate, register, validate and parse all answer the same question about the file they touched — what is in it, and does it conform — so they all print the same block: one header line naming what the command did, then an aligned label: value list whose first row is the sanity-check verdict. All four take --verbose / -v, which adds the resolved path, the times dtype and the three metadata groups. demo is the odd one out: it writes a file that deliberately does not conform, to practise parse on.

mesokit data avail¶

List the predefined simulator recipes compiled into the package (alias: mesokit data available). This is the catalog of what data generate can run, independent of what has been generated on this machine.

$ mesokit data avail
DYN                       SIMULATOR
allen_cahn_1d             mesokit.data.allen_cahn.allen_cahn_1d.simulate_allen_cahn_1d
cahn_hilliard_2d          mesokit.data.cahn_hilliard.cahn_hilliard_2d.simulate_cahn_hilliard_2d
ising_2d                  mesokit.data.ising.ising_2d.simulate_ising_2d
kdv_1d                    mesokit.data.kdv.kdv_1d.simulate_kdv_1d
llg_lattice_2d            mesokit.data.llg.llg_lattice_2d.simulate_llg_lattice_2d
peridynamics_fracture_2d  mesokit.data.peridynamics.peridynamics_fracture_2d.simulate_peridynamics_fracture_2d

The SIMULATOR column is the Python callable each recipe dispatches to; the physics, numerical scheme and parameters of every entry are documented in Predefined Datasets.

mesokit data list¶

List the datasets registered in .mesokit/datasets.json, grouped by dynamics. A dataset whose dyn attribute matches a predefined simulator is listed under that name; anything else lands in a trailing custom: group. The second column says whether the file still exists (yes) or the registry points at something that has been moved or deleted (MISSING).

$ mesokit data list
allen_cahn_1d:
  allen_cahn_1d_v0  yes  /home/me/mesokit/data/allen_cahn_1d/allen_cahn_1d_v0.h5
  ac_eps05          yes  /home/me/mesokit/data/allen_cahn_1d/ac_eps05.h5

kdv_1d:
  kdv_1d_v0         yes  /home/me/mesokit/data/kdv_1d/kdv_1d_v0.h5

custom:
  md_slab           MISSING  /scratch/md/slab_density.h5

With nothing registered it prints (no datasets).

mesokit data generate¶

Run a predefined simulator from a recipe, write the trajectories to HDF5, validate the file and register it.

mesokit data generate \
  --dyn DYN \
  [--config STEM] \
  [--name NAME \
  | --no-registry] \
  [--output PATH] \
  [--force] \
  [--verbose|-v] \
  [--set KEY=VALUE ...]

Option

Default

Meaning

--dyn DYN

required

Predefined dynamics name (one of mesokit data avail).

--config STEM|PATH

default

Recipe configs/data/DYN/STEM.yaml (working directory, then the installed package), or a path to any YAML file.

--name NAME

DYN_v<n>

Registry name for the result. A name that is already registered is refused before the solver runs, unless --force.

--no-registry

off

Write the file but do not register it. Mutually exclusive with --name.

--output PATH

data/DYN/<name>.h5

Where to write the HDF5 file. Parent directories are created. An existing file is replaced, with a warning on stderr; a directory is refused.

--force

off

Replace an existing registry entry of the same name. It says nothing about the file on disk, which is replaced either way.

--verbose, -v

off

Leave the solver’s own log in place, report progress as plain lines that survive a pipe, print the full metadata, and show the traceback if the simulator fails.

--set KEY=VALUE

none

Override one recipe key for this run; repeatable. KEY must be a keyword argument of the simulator; VALUE is read as int, float, bool (true / false) or string, in that order.

What happens, in order: the recipe is loaded with Hydra, the --set overrides are merged on top (an unknown key is rejected before anything runs), the registry name and the output path are checked (a taken name is refused, a directory is refused, an existing file warned about) so that a long solve cannot be spent on a run that cannot be recorded and cannot silently clobber a file, and the result is instantiated (every key in the YAML is a keyword argument of the simulator, and verbose is forwarded); the returned TrajectoryDataset is saved; the saved file is run through the same validator as data register; on success the registry entry is written and the summary is printed.

$ mesokit data generate --dyn allen_cahn_1d --config fdr --name ac_smoke
wrote data/allen_cahn_1d/ac_smoke.h5 (1019.3 KiB)
  check:      passed (mesokit-trajectory v1)
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u
  registry:   ac_smoke

dt is the one step of a uniform time grid, or non-uniform when the saved times do not sit on one to within the v1 tolerance — as here, where 101 float32 times a millisecond apart drift in the seventh digit. It describes the saved times rather than a validation failure. Training uses a fixed step; see Time step for how to set it.

-v keeps Dedalus’s per-step log and reports progress as one line per ten percent of the run. Both go to stderr — mesokit points the solver’s own log handler there — so the block below is still all of stdout, and the two streams stay separable in a log. It adds the rest of what the validator inferred:

$ mesokit data generate \
  --dyn allen_cahn_1d \
  --config fdr \
  --name ac_smoke \
  --force \
  -v
wrote data/allen_cahn_1d/ac_smoke.h5 (1019.3 KiB)
  check:      passed (mesokit-trajectory v1)
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u
  registry:   ac_smoke
  path:       /home/me/project/data/allen_cahn_1d/ac_smoke.h5
  times:      float32
  physical:   Lx=6.283185307179586  T=0.1  eps=0.1
  numerical:  Nk=3  Nx=256  T_save_steps=25  dealias=2  dt=4e-05  dx=0.02454369260617026  max_k=10
  provenance: seed=0  u_bound=10.0

With --no-registry nothing is validated, because that would mean reading the whole data array back for six printed lines; the block says so and names the command that does check it. Here on a second run onto the same --output, so the overwrite warning is there too:

warning: overwriting data/scratch.h5 (pass --output to write elsewhere)
wrote data/scratch.h5 (1019.3 KiB)
  check:      not run
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u
  registry:   not registered (--no-registry)
run `mesokit data validate data/scratch.h5` to check the file against the v1 contract.

The warning: line goes to stderr, before the simulator starts. Overwriting is allowed — sweeps and re-runs depend on it — so this is a warning, not the refusal data parse makes.

More examples:

# The reference dataset, auto-named allen_cahn_1d_v0 (then _v1, _v2, … on repeats).
mesokit data generate --dyn allen_cahn_1d

# A variant recipe: configs/data/ising_2d/kac.yaml (Kac interaction).
mesokit data generate --dyn ising_2d --config kac --name ising_kac_T07

# Write somewhere else and keep it out of the registry (scratch experiments).
mesokit data generate \
  --dyn cahn_hilliard_2d \
  --config fdr \
  --output /tmp/ch_test.h5 \
  --no-registry

# Re-run a recipe you changed and replace the previous entry of the same name.
mesokit data generate --dyn kdv_1d --name kdv_long --force

# Watch Dedalus's per-step log, and print the full metadata at the end.
mesokit data generate --dyn kdv_1d --config fdr -v

# One-off parameter change without a new recipe file.
mesokit data generate \
  --dyn allen_cahn_1d \
  --set eps=0.05 \
  --set seed=1 \
  --name ac_eps0.05_s1

To change parameters for good, add a sibling YAML under configs/data/<dyn>/ (copy default.yaml, edit, pick it with --config); for a one-off run use --set, and for a whole grid of values use mesokit sweep. Every predefined recipe also ships fdr.yaml, a seconds-long “fast dev run” for trying the pipeline. Some recipes are heavy — the default cahn_hilliard_2d takes about ten minutes and peridynamics_fracture_2d about twenty-five; the per-dataset sections of Predefined Datasets give sizes and timings.

Errors you may see:

Invalid value: no recipe dir configs/data/nope in any of: …
Invalid value: no config 'nope' under /home/me/mesokit/configs/data/allen_cahn_1d; available: default, fdr
Invalid value: --name and --no-registry are mutually exclusive
Invalid value: dataset 'ac_smoke' already registered; pass --force to overwrite
Invalid value: expected KEY=VALUE, got 'eps'
Invalid value: unknown parameter 'epsilon' for simulator mesokit.data.allen_cahn.allen_cahn_1d.simulate_allen_cahn_1d; accepted: eps, n_traj, Nx, Lx, T, T_save_steps, timestep, Nk, max_k, u_bound, dealias, seed, verbose
Invalid value: output data is a directory; pass --output with a file path
Invalid value: cahn_hilliard_2d: round(T/dt)=10 must be a positive multiple of save_every=20

For a custom simulator, check that its recipe is in your project’s configs/data/<dyn>/ directory, or pass a YAML path with --config. Built-in recipes are also looked up in the installed package and checkout.

The last one is the simulator itself rejecting the parameters it was given, prefixed with the dyn it came from; a --set that a recipe accepts but the solver cannot honour surfaces here rather than as a Hydra traceback, and the message ends with re-run with -v for the traceback. Only exceptions raised inside the simulator are summarised this way: a failure of the registry, the writer or mesokit itself keeps its stack rather than being reported as your parameters being wrong.

mesokit data register¶

Validate an HDF5 file you produced yourself against the v1 cache contract and register it under a name.

mesokit data register \
  --name NAME \
  --file FILE.h5 \
  [--force] \
  [--verbose|-v]

Option

Default

Meaning

--name NAME

required

Registry name.

--file FILE

required

Existing HDF5 file; the absolute path is stored.

--force

off

Replace an existing entry of the same name.

--verbose, -v

off

Also print the file path, the times dtype and the three metadata groups.

The validator checks the closed set of root attributes, the data / times datasets and their shapes and dtypes, finiteness, monotone times, the three metadata groups and the optional channel_names. Its verdict is the check: row: passed (in green on a terminal) naming the contract the file was checked against, and nothing is registered unless it says so.

$ mesokit data register --name ac_scratch --file data/scratch.h5
registered 'ac_scratch' -> /home/me/project/data/scratch.h5 (1019.3 KiB)
  check:      passed (mesokit-trajectory v1)
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u

With -v the same call adds what the validator read out of the file:

registered 'ac_scratch' -> /home/me/project/data/scratch.h5 (1019.3 KiB)
  check:      passed (mesokit-trajectory v1)
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u
  path:       /home/me/project/data/scratch.h5
  times:      float32
  physical:   Lx=6.283185307179586  T=0.1  eps=0.1
  numerical:  Nk=3  Nx=256  T_save_steps=25  dealias=2  dt=4e-05  dx=0.02454369260617026  max_k=10
  provenance: seed=0  u_bound=10.0

A file that is not a v1 cache fails on stderr, in red, with status 2 — the verdict first, then every failing check, then the reason nothing was written:

sanity check FAILED: /home/me/project/data/demo/allen_cahn_1d_demo.npz
  cannot open /home/me/project/data/demo/allen_cahn_1d_demo.npz as HDF5: Unable to synchronously open file (file signature not found)
Invalid value: sanity check failed for /home/me/project/data/demo/allen_cahn_1d_demo.npz; not registered

Writing a conforming file is a few lines of h5py; see Custom Datasets. To check a file without registering it, use mesokit data validate below (or the Python helper mesokit.data.validate(path)).

mesokit data validate¶

Check a file against the v1 contract and print the inferred metadata, without touching the registry. register runs the same check before it writes an entry, and the agent behind parse runs it on its own output.

mesokit data validate FILE [--verbose|-v]

$ mesokit data validate data/scratch.h5
validated /home/me/project/data/scratch.h5 (1019.3 KiB)
  check:      passed (mesokit-trajectory v1)
  dyn:        allen_cahn_1d
  shape:      10 traj x 101 steps x 1 channel, grid 256 (float32)
  dt:         non-uniform
  channels:   u

-v adds the path, times, physical, numerical and provenance rows shown under register above.

A non-conforming file names every failing check and exits with status 2. For the HDF5 form of the practice file mesokit data demo writes, that is:

sanity check FAILED: /home/me/project/data/demo/allen_cahn_1d_demo.h5
  missing required root attribute 'format'
  missing required root attribute 'version'
  missing required root attribute 'dyn'
  missing required root attribute 'data_dtype'
  missing required dataset 'data'
  missing required dataset 'times'
  missing required metadata group 'physical'
  missing required metadata group 'numerical'
  missing required metadata group 'provenance'
Invalid value: validation failed for /home/me/project/data/demo/allen_cahn_1d_demo.h5

mesokit data demo¶

Write a small, deliberately non-conforming dataset to practise mesokit data parse on, so you can see the conversion work without one of your own files.

mesokit data demo [--output PATH] [--format npz|h5]

Option

Default

Meaning

--output PATH

data/demo/allen_cahn_1d_demo.<format>

Where to write the file. Parent directories are created; an existing file is replaced with a warning.

--format

npz

npz for a NumPy archive (not HDF5 at all, so data validate cannot even open it), h5 for an HDF5 file that opens but is not a v1 cache, so the validator can list what it is missing.

The file holds a real 1-D Allen-Cahn run — four trajectories, 51 frames, 128 grid points, plain NumPy, fixed seed, no solver back-end — stored the way an outside code would leave it: axes in the order (frame, x, run) with no channel axis, integer frame indices instead of times, and flat scalars instead of the three metadata groups. Every fact the v1 cache needs is in the file; none of it is where the schema wants it. The content is a fixed-seed constant, so re-running writes the same arrays.

$ mesokit data demo
wrote data/demo/allen_cahn_1d_demo.npz (npz, 208.5 KiB)
  u            float64  (51, 128, 4)   field, axes (frame, x, run)
  x            float64  (128,)         grid coordinates
  frame_steps  int64    (51,)          solver iteration of each frame
  dt=0.001 eps=0.15 Lx=6.283185307179586 seed=0
not a v1 cache file: no root attributes, no 'times', no metadata groups.
convert it with an agent:
  mesokit data parse --file data/demo/allen_cahn_1d_demo.npz --name allen_cahn_demo_v0

Two strings the block does not print are in the file as well: equation (u_t = u_xx + (u - u**3) / eps**2, periodic in x) and notes, which spells out that frame times are frame_steps * dt — the one fact the arrays alone do not give away.

--format h5 writes the same run into an HDF5 container and adds a line pointing at mesokit data validate, which then names all nine violations (the block is under data validate above).

Errors: unknown format 'nc'; available: npz, h5, and the same output … is a directory refusal data generate makes.

mesokit data parse¶

Hand an arbitrary dataset to a coding agent installed on your machine, let it convert the file with the mesokit-convert-data skill shipped in the package, then validate (and optionally register) the result. The skill itself, and the five others that cover training and extending, are described in Agent Skills; mesokit skills installs them into an agent for conversational use.

mesokit data parse \
  --file FILE \
  [--output PATH] \
  [--hint TEXT] \
  [--agent claude|codex] \
  [--backend foreground|tmux] \
  [--agent-args "FLAGS"] \
  [--name NAME] \
  [--force]

Option

Default

Meaning

--file FILE

required

Input in any format (.npz, .npy, .nc, .pt, non-conforming .h5, …). It may live outside the working directory.

--output PATH

data/parsed/<stem>.h5

Where the agent must write the v1 file. Must not exist yet, unless --force is given.

--hint TEXT

none

Free-form instructions appended to the agent’s prompt (axis names, units, which variable is the field, …).

--agent

claude

Agent CLI: claude (runs claude -p …) or codex (runs codex exec …). Checked first: if the command is not installed, parse stops and prints the official installation guide to follow.

--backend

foreground

foreground blocks and streams the agent’s output; tmux detaches into a session.

--agent-args "FLAGS"

none

Extra flags for the agent command, split like a shell and appended after the built-in ones: "--model opus", "--allowedTools Bash(uv run:*)", "-c model=o3".

--name NAME

none

Register the produced file under this name on success. Without it the file is only validated.

--force

off

Replace an existing output file, and an existing registry entry of the same name.

Before anything is created or launched, the command checks that the agent’s CLI (claude or codex) is installed in the shell it runs in. If it is not, it exits at once and names the official installation guide: Claude Code or the Codex CLI. Install the agent there, confirm claude --version (or codex --version) works, and re-run.

What the agent may do. The agent runs non-interactively (claude -p, codex exec), so nothing can be approved once it has started: parse grants what a conversion needs on the command line, no more, and prints that command line (the argv line below) so the grants are visible. It works from any directory, a plain folder that is not a git checkout included; the agent’s working directory is the one you run mesokit in.

  • claude: --permission-mode acceptEdits, which auto-approves file writes inside the working directory and nothing else; --allowedTools listing the Bash commands python, python3, the interpreter mesokit itself runs in, mesokit and pixi run; and --add-dir for the input’s and the output’s directories when they lie outside the working directory. Neither --dangerously-skip-permissions nor bypassPermissions is used.

  • codex: the workspace-write sandbox (commands may write under the working directory and read anywhere; no network), set as -c sandbox_mode=workspace-write so that a --sandbox given through --agent-args overrides it; --add-dir for an output directory outside the working directory; and --skip-git-repo-check.

For both, stdin is closed (/dev/null; each CLI would otherwise read a piped stdin as more prompt). A different model, a wider allowlist or another sandbox go through --agent-args, for example --agent-args "--sandbox danger-full-access" on a machine where Codex’s bubblewrap sandbox cannot start.

The prompt. The skill’s text is embedded in the prompt — nothing outside the project has to be readable — together with the input and output paths, the interpreter to use (the one mesokit runs in, so a pipx install works too), the self-check <python> -m mesokit data validate <output> to repeat until it passes, and your --hint. The agent is told not to register anything; parse does that itself on return.

On return. In the foreground backend the command returns when the agent exits. A non-zero exit, or an output file the agent did not write, is an error. A file that already sits at the output path is refused before the agent is launched (with --force it is removed first), so what gets validated is always the agent’s own work.

If you have no file of your own to hand, mesokit data demo writes one to practise on; the run below is exactly that, start to finish:

$ mesokit data demo
$ mesokit data parse --file data/demo/allen_cahn_1d_demo.npz --name allen_cahn_demo_v0
launching agent 'claude' via backend 'foreground'
  skill : /home/me/.venv/lib/python3.12/site-packages/mesokit/skills/mesokit_convert_data/SKILL.md (embedded in the prompt)
  input : /home/me/project/data/demo/allen_cahn_1d_demo.npz
  output: /home/me/project/data/parsed/allen_cahn_1d_demo.h5
  argv  : claude -p --permission-mode acceptEdits --allowedTools 'Bash(python:*),…' -- <prompt>
… agent transcript …
registered 'allen_cahn_demo_v0' -> /home/me/project/data/parsed/allen_cahn_1d_demo.h5 (213.7 KiB)
  check:      passed (mesokit-trajectory v1)

The agent transposed (frame, x, run) into (traj, time, channel, x), inserted the channel axis, turned frame_steps * dt into times, and split the flat scalars across physical / numerical / provenance. The exact choices vary between runs; the check: row is what says the result conforms. Without --name the tail reads validated <path> instead, followed by pass --name to also register this dataset.

Your own file works the same way, with --hint carrying whatever the arrays do not say for themselves:

mesokit data parse \
  --file ~/runs/burgers.npz \
  --hint "arrays u (traj, time, x) and t; domain is [0, 2π) periodic; call it burgers_1d" \
  --name burgers_v0

With --backend tmux the command returns immediately and tells you how to follow up:

agent launched detached (handle: mesokit-parse-1756800000)
  attach: tmux attach -t mesokit-parse-1756800000
when the agent finishes, validate / register with:
  mesokit data register --name burgers_v0 --file /home/me/mesokit/data/parsed/burgers.h5
